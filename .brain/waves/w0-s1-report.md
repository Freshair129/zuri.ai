## Routes needing a new requirement

- **src/app/(pm)/timeline/page.jsx** — Cross-project Timeline: a read-only month-grid visualization that plots every Project's `startAt`→`targetAt` window and every Milestone's `targetAt` across the active scope on one shared axis, with status coloring per bar. Draft statement: *"A cross-project Timeline view renders all in-scope Projects' date windows and Milestones' target dates on one comparable time axis, read-only, with no new persistence."* No existing FR declares this synthesis of FR-003 (project dates) and FR-006 (milestone dates) into a single view; it is not mentioned by FR-009 (execution views), FR-040/SDD-019 (which only cover the project-local Dependency Map and Structure Plan), or FR-058 (File Manager's unrelated "timeline" ordering mode).

## Notes and doubts

- **The "Universal views" cluster (dependencies, milestones, work; timeline is the odd one out).** `docs/ARCHITECTURE.md` and `docs/ROUTES-SITEMAP.md` both name a "Universal Views" / Development-sidebar group (`Projects · All Work · Execution · Timeline · Dependencies · Milestones & Gates · Repositories`) but neither is the requirement registry — they describe routing/layout, not FR coverage. For dependencies/milestones/work I anchored on the underlying `application/*.js` service's `@req` (per the survey's sibling-alignment instruction) because each page is a thin, unscoped (`projectId` omitted) rendering of exactly that service's entity — same pattern the codebase already uses elsewhere (e.g. `src/app/(pm)/backup/page.jsx` → FR-013 even though FR-013's text doesn't say "UI"; `src/app/(pm)/people/page.jsx` → FR-042). I marked these **MEDIUM** rather than HIGH because, unlike FR-014 ("+ UI browser") or FR-042 ("People Directory"), none of FR-005/006/007's text names a UI surface explicitly — only the audit precedent is that explicit. A controller could reasonably decide these three deserve their own new FR each (e.g. "cross-project Dependencies/Milestones/Work browsing view") instead of piggybacking on the data-model FR; I did not choose that path because the pages add no capability beyond CRUD/list/status-change on the exact entity the existing FR already declares, and the repo's own convention (page ↔ underlying-service FR) already treats that as sufficient.
- **FR-040 / SDD-019 explicitly distinguishes** the project-local Dependency Map (owned by FR-040, lives at `/projects/{id}/dependencies`) from "the cross-project register [that] remains Development → Dependencies" — i.e. this survey's `src/app/(pm)/dependencies/page.jsx`. That sentence confirms the global page is a *different, older* thing than FR-040's map (so FR-040 is the wrong anchor for it), but it does not itself assign the global page an id. I used FR-007 instead, per the reasoning above.
- **src/app/(pm)/workspaces/[workspaceId]/page.jsx** is a closer call than the plain workspaces list: it does no CRUD itself (no edit/archive controls), it just resolves one Workspace's identity from the FR-001 scope model and lists its Projects (an FR-003 read). I anchored on FR-001 since the page is keyed by `workspaceId` and its header/eyebrow are entirely about the Workspace entity (code, scopeType, name) rather than about Projects generically — but FR-003 is a defensible second choice if a controller reads it as "Projects, filtered by Space" instead. Flagging both readings rather than picking one silently.
- **No dead routes observed** among the 11 — all render real data through the existing API surface and none look orphaned or superseded.
- **FR-009's Thai text says "global + project-scoped" explicitly**, which is the strongest, most literal registry match found in this batch — stronger even than the audit page's match, since it names the exact global/project-scoped split that `execution/page.jsx` + `execution/[mode]/page.jsx` (global) vs. `projects/[projectId]/execution/[mode]/page.jsx` (project-scoped, not in this batch) implement.
