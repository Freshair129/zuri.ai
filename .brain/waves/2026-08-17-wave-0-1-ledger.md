## Constraints that shape the schedule

- **One port, one e2e database.** `playwright.config.js` binds :3100 with
  `reuseExistingServer: false`, and the suite seeds a single `prisma/e2e.db`.
  Only one lane may run e2e at a time — this is why Lane T runs alone.
- **Worktree isolation is unavailable in practice.** A fresh git worktree has no
  `node_modules`, so an agent there cannot run the tests that would prove its
  work. Lanes therefore share the tree and are separated by *file*, not by
  checkout.
- **Id allocation cannot be parallel.** Two sessions already collided on
  ADR-020; the duplicate-id guard exists because of it. All new FR/SDD ids are
  allocated by the controller in one commit before any lane needs them.
- **`docs/.viewer-fixture-baseline.json` is a single shared surface.** Three
  repayments in three lanes would all shrink it. One agent owns all three.

### Why Lane T is held rather than dispatched now

Its first step is *measurement* — does `--workers=1` remove the flakiness — and
the thing being measured is behaviour under machine load. Running it while four
surveys and a test suite occupy the machine would load the box with the very
variable under test, and produce a number that means nothing.

That confound has already overturned two conclusions in this session, both
times because the difference was *when* something ran rather than *what* ran.
Lane T starts when the machine is otherwise idle.

### Git is single-writer: the controller

Lanes share one working tree, so no lane branches, commits, stashes or pushes.
Agents leave edits in the tree; the controller stages them by path into separate
commits and drives the merge train. A lane that ran `git stash` mid-flight would
take another lane's uncommitted work with it.

## Controller decisions taken during Wave 0

**D1 — a "browse-all" page anchors on the existing requirement, whose text is
sharpened to name the surface.** Raised by S1: `dependencies`, `milestones` and
`work` pages deliver behaviour declared by FR-007 / FR-006 / FR-005, but those
statements describe the data model, not a screen. The alternative was minting
three new FRs.

Rejected, because three near-duplicate ids that nothing else references make the
registry *less* navigable, and the id contract's prohibition is on renumbering
and on reusing an id for a **different** statement — not on stating the same
requirement more completely. FR-014 already names its own UI ("+ UI browser"),
so the registry has the precedent. Same move as FR-059 and SDD-017 earlier
today.

**D3 — Board and Schedule get new ids; S2's recommendation was overridden.**
S2 proposed widening FR-040's text to cover them, consistent with D1. Rejected,
and the line between the two cases is the useful part:

| | FR declares the behaviour? | Move |
|---|---|---|
| browse-all pages (D1) | yes — text just never names the screen | sharpen the statement |
| Board / Schedule | **no requirement anywhere describes a status board or a date grid** | mint a new id |

*Unstated surface for stated behaviour* is an incomplete sentence. *Unstated
behaviour* is a missing requirement. Widening FR-040 would have put new
requirement content under an existing key — the one thing the id contract
forbids. SDD-019 had asserted its tab owned four sub-views while its FR stated
two, so two shipped with nothing behind them; it now cites FR-063/FR-064.

**D4 — a guard that makes people move code to avoid it is fixed, not obeyed.**
Lane F relocated a Membership DB mock into a new fixture file purely to escape
the ratchet's proximity window, and documented the workaround in that file's
header. Both halves are the wrong outcome: the workaround becomes the lesson,
and the signal weakens everywhere else. The heuristic now suppresses a `role:`
that sits on a line carrying Membership-only fields (`personId`,
`domainKeysJson`, `employeeRef`, `branchId`, `tenantId`) — provably DB data, never
a viewer. The mock moved back next to its tests. Proven in both directions: a
planted hand-built viewer is still caught; the Membership rows no longer fire.

**D2 — the controller's own steer was wrong about `/api/scope`.** The brief told
S4 to expect NONE for `/api/scope` and `/api/resolve`. S4 disagreed, said so
explicitly, and was right: `scope-service.js` carries `@req FR-001` and a
FR-020 branch. Verified directly. Recorded because a survey that contradicts its
brief and flags the contradiction is the behaviour worth having.

## Gates

Worker → verify gate (separate agent, never self-review) → **controller runs the
full suite itself on integrated main**. The session record is that seven agents
and two gates reported e2e green while the full suite was red.

## Merge protocol

PRs prepared in parallel, merged **one at a time**. Each rebases and re-runs
`npm run govern` before entering the queue: six generated files are rewritten by
every branch and CI fails if a branch ships a stale one. Conflict resolution
there is mechanical — take theirs, regenerate.
