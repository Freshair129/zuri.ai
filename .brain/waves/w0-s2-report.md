## Routes needing a new requirement

- **src/app/(pm)/projects/[projectId]/board/page.jsx** — a project-scoped Kanban board: every WorkItem in the project, grouped into six canonical statuses (Backlog/To Do/In Progress/In Review/Blocked/Done), read-only (status changes still go through the existing services), reached as the "Board" sub-view of the Project `Work` tab. Draft statement: *"The Project Work tab's Board sub-view renders every WorkItem in the opened Project grouped by its canonical status into a read-only Kanban layout; status transitions continue through the existing WorkItem services, and no new persistence is introduced."*

- **src/app/(pm)/projects/[projectId]/timeline/page.jsx** — a project-scoped read-only Gantt-style view plotting the Project's own date window and its Milestones' target dates on one month grid. Draft statement: *"The Project Work tab's Schedule sub-view renders the opened Project's own `startAt`/`targetAt` window and its Milestones' `targetAt` dates on one comparable time axis, read-only, with no new persistence."* Note this is the project-contained analogue of the requirement W0-S1 already drafted for the global `/timeline` page — the controller may want one statement covering both scopes (project-scoped **and** cross-project) the same way FR-009 covers execution views at both scopes in a single clause, rather than two near-duplicate ids.

## Is one requirement enough?

No — this batch of 7 splits cleanly into three groups, and forcing them into one id would either overreach (bundling unrelated entities) or hide a real gap:

1. **Already covered by an existing, independently-declared requirement (5 of 7):** `all-work` → FR-005, `execution/[mode]` → FR-009, `import` → FR-012 (+BR-009, FR-018), `milestones` → FR-006, `repositories` → FR-008. These five ride on requirements that exist for reasons unrelated to FR-040/the Work tab (the neutral work model, the seven execution modes, the import pipeline, milestones/gates, repository links) — each already has its own registry statement, its own service-level `@req`, and (for `all-work`/`milestones`/`repositories`) an already-anchored global sibling from the W0-S1 survey. Annotating these five is a citation exercise, not a new-requirement exercise.

2. **Named by the Work-tab shell but never specified (2 of 7):** `board` and `timeline`. FR-040's actual PRD statement and its acceptance criteria/tests are scoped to exactly two visualisations — Structure Plan and Dependency Map (`structure/page.jsx` and `dependencies/page.jsx` already carry `@req FR-040` and are the only two "Surface" entries FR-040 has in `docs/TRACE.md`). SDD-019 additionally *names* Board and Schedule as things the Work tab "owns," and `WorkViewTabs`/`tests/unit/project-work-route.test.js` confirm the tab *links* to them — but nothing in the registry describes what either page should render. This is precisely the "tab shell vs. the page" distinction the task flagged: the shell (`layout.jsx`, `ProjectTabs.jsx`, `WorkViewTabs.jsx`) is FR-040's declared territory; the Kanban-board and Gantt-timeline content behind those two links is not.

   These two are one requirement or two, not zero — a controller has a real choice: (a) extend FR-040's own statement to explicitly claim "Board" and "Schedule" alongside Structure Plan and Dependency Map (cheapest, matches SDD-019's existing "owns" language, and keeps one id for "the Work tab's four sub-views"), or (b) mint one new id per sub-view. I lean toward (a) — SDD-019 already asserts ownership of all four, so widening FR-040's stated scope to match its own design decision is smaller than inventing new ids for content that was already conceptually claimed, just never written into the FR text.

3. **No sensible shared id (0 remaining, but worth stating):** `all-work`, `milestones`, and `repositories` might look like a group ("other project resource surfaces"), but they aren't one requirement even hypothetically — they already resolved individually to FR-005/006/008 above, and those three FRs have nothing in common except being project-manager domain models. The repo's own precedent (FR-036 Team, FR-037 Files, FR-038 Profile — each its own id even though all three are "project/business resource surfaces") argues against ever bundling unrelated entities under one umbrella id.

## Notes and doubts

- **`board` and `timeline` are the genuinely hard calls, and the peer W0-S1 survey independently reached the same conclusion for `timeline`'s global sibling** (`src/app/(pm)/timeline/page.jsx` → NONE, "not mentioned by FR-009..., FR-040/SDD-019 (which only cover the project-local Dependency Map and Structure Plan)"). I'm treating that as corroboration rather than re-litigating it. `board` has no global sibling to cross-check against (there is no `src/app/(pm)/board/page.jsx`), so its NONE verdict rests on the FR-040 text + AC-040-01 test scope alone; a controller who reads SDD-019's "owns" language more liberally than I did could reasonably call it EXISTING at LOW-MEDIUM confidence instead. I chose NONE because the one test that exercises FR-040's acceptance criterion for Board/Schedule (`tests/unit/project-work-route.test.js`) only asserts the *label text* exists in the tab bar — it never opens `board/page.jsx` or `timeline/page.jsx`, so there is no tested behavioural claim to point `@req` at.
- **`timeline/page.jsx` doesn't render `WorkViewTabs`** (unlike `structure`, `dependencies`, and `board`, which all do) — a small implementation inconsistency, not a requirements question, but worth flagging separately since it means a user landing on `/projects/{id}/timeline` currently has no way to reach the other three Work sub-views from that page.
- **`import/page.jsx`'s workspace targeting is not strictly project-bound** — `PlanImportPanel` accepts an independent `workspaceId` override, defaulting to the opened project's workspace only when unset. This is consistent with FR-012 being a workspace-scoped pipeline that happens to be reachable from a Project's nav for convenience, not evidence against the FR-012 anchor.
- **Sibling-alignment method used per the task's step 4:** for `all-work`, `milestones`, and `repositories` I aligned to the underlying `application/*.js` service's existing `@req` tag (`work-service.js` → FR-005, `milestone-gate-service.js` → FR-006, `repository-service.js` → FR-008) and to the W0-S1 survey's identical verdict on each page's global counterpart, since both pages share the same view component and the same service. I did not find an equally strong sibling to lean on for `board`/`timeline` — the one component both share (`WorkViewTabs.jsx`) only carries an `@req FR-040` comment about the Dependency Map specifically ("Project Work owns the project-local Dependency Map sub-view"), not about Board or Schedule content.
- **Confidence calibration:** HIGH where the registry text names either an explicit UI-surface word ("UI browser", "views", or — via BR-009 — "UI" as an intake-surface type) or an exact behavioural/relationship match (`repositories`' many-to-many link modal); MEDIUM where the FR names the entity/fields precisely but never mentions a surface at all (`all-work`, `milestones`), matching the calibration the W0-S1 report already established for these same two entities.
