## Did the factory refuse anything?

No. Every shape these three files needed — a fully-owning OWNER, a plain MEMBER, an OWNER scoped to exactly the Businesses it can see, and the OWNER-of-A/MEMBER-of-B attacker shape — is directly expressible through `makeViewer()`/`ownsElsewhere()`, most of it already named by the factory (`ownsElsewhere` is literally this attack pattern).

One thing worth flagging as a genuine finding, not a factory refusal: `docs/.viewer-fixture-baseline.json`'s companion check (`scripts/doc-preflight.mjs`, Check 8) detects hand-built viewers with a **proximity heuristic** — `role: 'OWNER'|'MEMBER'|'DEV'` within 10 source lines of any viewer-field name (`visibleBusinessIds`, `ownedBusinessIds`, `domainsByBusinessId`, `visibleDomains`, `isPlatform`). This heuristic cannot distinguish "a viewer literal" from "a Membership DB-row mock that happens to have a `role` column" or "an expected-response literal that happens to mirror the viewer DTO's field names." Two false positives surfaced during this repayment:
1. `people-service.test.js`'s `dbFor()` mock returns Membership rows with `role: 'OWNER'`/`role: 'MEMBER'` — legitimate Prisma-shaped fixture data, not a viewer — but its proximity to the new `visibleBusinessIds` usage in the same file tripped the check. Fixed by moving the DB-row fixture to its own file.
2. `fr046-entry-contract.js`'s `OWNER_ENTRY_RESPONSE.viewer` object is the *expected JSON output* of `buildViewerEntry()`, not a viewer being constructed for authorization — but it independently contains `role: 'OWNER'` near `visibleDomains`/`isPlatform`. Fixed by deriving those fields from `OWNER_VIEWER` instead of retyping the string, which also removed a small duplication.
Also avoided, on principle rather than necessity: passing an explicit `role: 'OWNER'`/`'MEMBER'` literal to `makeViewer()` calls anywhere a caller can instead pass `ownedBusinessIds` and let the factory infer the role — this sidesteps the heuristic entirely and matches how the reference repayment (`profile-permission-service.test.js`) was already written.

## Concerns

The false-positive proximity heuristic in Check 8 (see above) is not specific to this repayment — any future test file that legitimately mixes a `role:`-bearing Membership/DTO literal with viewer-field vocabulary within ~10 lines will trip it and either need restructuring (as done here) or a baseline entry (which the rules forbid adding). Flagging this as a structural fragility in the ratchet itself, out of scope to fix here since it lives in `scripts/doc-preflight.mjs`, not the three files assigned.
