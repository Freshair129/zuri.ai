# PM review R3 — intake pipeline

Scope reviewed: `src/modules/project-manager/import/` (plan-schema.js, plan-import-service.js, external-ref.js, xlsx-convert.js, xlsx-template.js), the three `/api/import/*` routes, `/api/resolve`, the UI callers (`PlanImportPanel.jsx`, `projects/new/page.jsx`), the agent/LINE surface, `/api/backup/import`, `contracts/plan-envelope.schema.json`, and the declared rules (FR-012/018/019, BR-002/007/009, SEC-002, SDD-009).

## Findings

### F1 — Child entities are upserted by globally-unique code with no ownership check: a plan can silently overwrite another project's workstreams, items, containers, milestones and gates
- **Where**:
  - Dry run: `D:\zuri-ai\src\modules\project-manager\import\plan-import-service.js:130-139` — `classify()` for containers, items, milestones and gates is called with **no** `extraConflictCheck`; the workstream check at :131-135 only fires when `existingProject` is non-null (i.e. it is skipped whenever the plan's project is a new insert).
  - Commit: `plan-import-service.js:193-204` (`write()` upserts `where: { code }`), item update branch :294-306, milestone :328, gate :345-349.
- **How it fails**: every `code` column is `@unique` **globally** (`prisma/schema.prisma` — one namespace across all workspaces/projects). Envelope: import project `BETA` into workspace W2, with a workstream containing an item whose `code` equals `ITEM-1`, an item that already belongs to project `ALPHA` in workspace W1. Dry run classifies `ITEM-1` as a benign `update` (no ownership check exists for items). Commit then:
  1. Overwrites ALPHA's item title, subtype, status, weight, metrics and metadata (:295-305) — the update object never re-checks or reassigns `workstreamId`, so the record stays inside ALPHA's workstream while carrying BETA's content;
  2. If the plan gives the item a `containerCode`, sets `containerId` to a container in **BETA** (:299), producing an item whose workstream is in W1 and whose container is in W2 — cross-workspace corruption no service can produce;
  3. The imported `subtype`/`metrics` were semantically validated against the **plan's** workstream mode (`plan-schema.js:201-208`), not against ALPHA's workstream `executionMode`, so ALPHA's workstream can end up holding an item subtype its mode contract forbids (breaks the BR-004 mode contract the semantic check exists to enforce, and the pure progress calculators that trust it).
  Same gap for containers, milestones and gates (updates mutate the foreign record in place; `projectId`/`workstreamId` untouched). For workstreams it also fires whenever the plan's project is new: dry run shows `project: insert, workstream: update`, commit renames/re-modes another project's workstream and then attaches all the plan's new items to it.
- **Evidence**: reachable from every surface — `/api/import/commit` (`src/app/api/import/commit/route.js:10`) called by both UI callers (`PlanImportPanel.jsx:99`, `projects/new/page.jsx:162`), and the xlsx flow which converges on the same commit endpoint. No authz/visibility layer intervenes (the routes have none). The project entity itself *is* protected (workspace + business checks at :123-128), which shows the check was known to be needed — it just was never applied to children.
- **Severity**: HIGH — the preview lies (reports a cross-project hijack as a routine "update") and the commit mutates data outside the plan's declared scope.
- **Declared rule it violates**: BR-009/SDD-009 (the dry run's job is to predict the commit; here it predicts an update of *your* entity while committing an update of *someone else's*), BR-004 (mode contract broken for the foreign workstream). Scope-chain isolation (docs/PRODUCT.md scope chain) for the cross-workspace `containerId` re-point.

### F2 — Commit throws (P2025, full rollback) on a plan the dry run declared valid: container matched by external id under a new code, plus `parentCode`
- **Where**: `D:\zuri-ai\src\modules\project-manager\import\plan-import-service.js:281-288` (second-pass parent linkage) vs `write()` at :196-198.
- **How it fails**: FR-019's design lets an external id match an existing record whose `code` differs from the plan's code (`resolveEntityIdentity` returns `matchedBy: 'externalRef'`, `matchedCode ≠ code`; the plan's code is verified to belong to *no* record, else it conflicts — `external-ref.js:85-89`). `write()` correctly updates that record by internal id and leaves its code alone. But the parent-linkage second pass updates `where: { code: c.code }` — the **plan's** code, which by construction does not exist in the database for this record. Prisma `update` on a missing row throws P2025, the `$transaction` rolls back, and `/api/import/commit` returns 500 ("Record not found" class) for an envelope the immediately-preceding dry run inside `commitPlan` reported as `valid: true` with a clean preview.
  Concrete envelope: container previously imported as `code: "OLD-STAGE"` with `externalRefs: [{system:"SAP", id:"C-77"}]`; re-import sends the same external ref under `code: "NEW-STAGE"` **and** any `parentCode`. Dry run: `update (matchedBy externalRef)` — commit: exception.
- **Evidence**: reachable via `/api/import/commit` from either UI. Containers accept `externalRefs` in both the Zod schema (`plan-schema.js:30`) and the JSON contract, and `parentCode` is an ordinary container feature; nothing rejects the combination earlier.
- **Severity**: MEDIUM — atomicity holds (no residue), but the pipeline's core promise "preview predicts the commit" is broken, and the failure surfaces as an unexplained 500 after a green preview.
- **Declared rule it violates**: BR-009/SDD-009, FR-019 (the relabel-by-external-id flow is exactly the advertised feature that trips it).

### F3 — Status, project type, repository provider/role are never validated against the enum source of truth; commit writes arbitrary strings the rest of the system cannot see
- **Where**: `D:\zuri-ai\src\modules\project-manager\import\plan-schema.js:28, 40, 54, 64, 107-108` (`status: z.string().optional()`, `type: z.string().optional()`) — while `src/lib/validation/enums.js:104-108` exports `zProjectStatus`, `zWorkStatus`, `zMilestoneStatus`, `zGateStatus` precisely for this. Commit writes the raw strings: `plan-import-service.js:217-218` (project), :265/274 (container), :298/313 (item), :328/334 (milestone), :347/356 (gate), :368/371 (repository provider), :378 (role).
- **How it fails**: envelope with `"status": "CANCELED"` (one L) or `"status": "done"` on a work item passes Zod, passes the semantic check (which validates `executionMode`, `progressStrategy`, `subtype` and metric keys — but never `status`), passes dry run, and is committed. The row then silently vanishes from or misbehaves in every view that switches on the enum — the exact defect class fixed in commit 7cba2ab ("board and sprint view dropping CANCELLED work"), except this variant is injectable at will through the pipeline and no code path can ever render it. A gate imported with `status: "PASSEDD"` is neither open nor satisfied (`SATISFIED_GATE_STATUSES`), wedging gate logic.
- **Evidence**: all three import surfaces reach it; the xlsx template constrains some columns via dropdowns, but the dropdown is client-side courtesy — `xlsx-convert.js` copies the cell text verbatim, and the JSON/UI surfaces have no dropdown at all. Note the JSON contract (`contracts/plan-envelope.schema.json:65-67` etc.) is equally loose (`"status": {"type":"string"}`), so contract and Zod agree with each other — both disagree with the enum SSOT rule.
- **Severity**: MEDIUM — no execution, no cross-tenant write, but the pipeline's validation leg admits data the rest of the system is contractually blind to.
- **Declared rule it violates**: the enum SSOT rule (CLAUDE.md "Enums are strings in the database, with `src/lib/validation/enums.js` as the single source of truth… validation all derive from it"; recently gated per commit 27eacdb). Against FR-012's "semantic contract check" it is a coverage gap; the JSON contract itself declares no enum here, so partially "none — undeclared behaviour" at the contract level.

### F4 — Commit performs writes the dry run never reports: ProjectRepository link creation with a defaulted role, and dependency creations reported only as a count
- **Where**: `D:\zuri-ai\src\modules\project-manager\import\plan-import-service.js:378-386` (`role = r.role || 'REFERENCE'`; `projectRepository.create`) and :389-402 (dependency creates). Dry-run counterpart :143-150 reports only repository insert/update and a raw `dependencyCount`.
- **How it fails**: the preview lists the repository row itself but says nothing about the project↔repo link that commit will create, nor the `role` it will default to `'REFERENCE'` when the envelope omits it (`role` is also an unvalidated free string — F3). Likewise `dependencyCount` counts every dependency in the plan, while commit creates only those that don't already exist — a re-import previews "5 dependencies" and creates 0. Cascading creates and defaulted fields the preview does not disclose.
- **Evidence**: any envelope with a `repositories` or `dependencies` array through any surface.
- **Severity**: LOW — writes are inside the transaction and scoped to the plan's own project; the defect is preview fidelity only.
- **Declared rule it violates**: BR-009/SDD-009 (preview must predict the commit).

### F5 — Identity resolution and preview are computed outside the commit transaction (TOCTOU); a concurrently-created ExternalRef mapping is silently re-pointed
- **Where**: `D:\zuri-ai\src\modules\project-manager\import\plan-import-service.js:177-184` (`dryRunPlan` runs before `$transaction`; `resolution` is reused inside it), with `external-ref.js:97-111` (`syncExternalRefs` upsert whose `update` branch unconditionally rewrites `entityType`/`entityId`).
- **How it fails**: between `commitPlan`'s internal dry run and the transaction, another commit can (a) create a record with one of the plan's codes — the predicted "insert" silently becomes an update of that new record; or (b) create the ExternalRef mapping the plan carries — `syncExternalRefs`' update branch then re-points that mapping at this plan's record, stealing the customer id from whatever record legitimately owns it, with no conflict raised (the dangling/wrong-type checks ran only in the stale pre-transaction read).
- **Evidence**: both `/api/import/commit` and any FR-019 integrator hitting the API concurrently. On the SQLite dev setup writes serialize, so the window is small; the Postgres/Supabase target (FR-030) makes it real.
- **Severity**: LOW today (SQLite), MEDIUM after the Postgres cutover.
- **Declared rule it violates**: SDD-006/BR-009 in spirit (the "single transaction" does not cover the reads its writes depend on); FR-019's "one external id points at exactly one record" invariant can be violated by the steal.

## Checked and found sound

- **No execution from data (BR-007/SEC-002)**: no `eval`, `new Function`, dynamic `require`, `child_process`, or template-to-code anywhere in `import/`. The only dynamic model dispatch (`prisma[model]`, `KIND_TO_ENTITY_TYPE`, `ENTITY_TYPE_TO_MODEL`, `KIND_TO_ENDPOINT`) is keyed by hardcoded call-site literals, never by envelope content. `metadata`/`metrics`/`evidence` are stored as JSON strings and consumed as data (`safeParse` in work-service/progress-service, `JSON.parse` in views) — never interpreted.
- **Strictness (SEC-002)**: `.strict()` on every object in `plan-schema.js`, matching `additionalProperties: false` in `contracts/plan-envelope.schema.json` at every level. The xlsx converter builds envelopes from a fixed column map, so no extra keys can enter through it either. (`z.record(z.any())` for metadata mirrors the contract's open `"type": "object"` — declared, not a strictness loss.)
- **One pipeline (BR-009)**: every reachable plan-shaped intake converges: UI JSON panel and the project wizard call `/api/import/dry-run` + `/api/import/commit`; the xlsx route converts then calls `dryRunPlan` and explicitly defers commit to the shared endpoint; the converter itself touches no database. The agent/LINE surface (`src/modules/agent`) performs no project-manager entity writes at all (only `identityLinkToken` + audit). `/api/backup/import` is a separate *declared* restore surface (FR-013/FR-045, BR-008), not an undeclared second plan-intake path. Single-entity CRUD goes through `application/` services as declared.
- **Dry run is read-only**: `dryRunPlan`, `resolveEntityIdentity`, `lookupExternalRef`, `resolveImportWorkspaceId`, and `workbookToEnvelope` issue only `findUnique` reads; nothing mutates, so an exception mid-dry-run leaves no residue.
- **External ids never keys (BR-002)**: incoming `{system, id}` is resolved through the `ExternalRef` table to an internal UUID; writes target `where: { id: internalUuid }`; the customer id never becomes `code` and never keys an entity table. Duplicate claims within a plan are rejected (`plan-schema.js:156-167`); cross-type and multi-target matches conflict rather than guess.
- **Commit is one transaction, audit included**: all entity writes, external-ref syncs, repository links, dependencies, and the `recordAudit(tx, …)` call sit inside the single `prisma.$transaction` (`plan-import-service.js:184-422`). No `progressCache` or any other write occurs outside it in the import path.
- **Commit re-runs the dry run and refuses on conflicts** (:178-181), so a stale client-side preview can never force a commit past a conflict that has since appeared.
- **Zero-test/green-suite integrity of the module's claims**: `@tested` files exist (`tests/integration/plan-import.test.js`, `external-ref-import.test.js`, `xlsx-intake.test.js`) — not executed per review rules.

## Uncertain

- **Gate state via import**: an envelope can set a gate to `PASSED` with arbitrary `evidence`, bypassing whatever ceremony `milestone-gate-service` applies. It flows through the audited pipeline (action `PLAN_IMPORTED`) and `PASSED` is a legal enum value, so this may be intended "import current state" semantics — flagging for a product-level ruling rather than as a defect.
- **Audit actor attribution**: `commitPlan` hardcodes `actorType: 'AGENT_PLAN'` (`plan-import-service.js:408`) even for human uploads via the UI/xlsx surfaces. The audit trail is complete but misattributes the actor class. No declared rule pins actorType per surface, so listed here.
- **No authorization on import routes** (`/api/import/*` accept any `workspaceId`): consistent with the rest of the API surface (e.g. `/api/projects` also has no viewer gate), so this looks like a platform-wide posture rather than an intake-specific hole; noting because F1's blast radius depends on it.
