# PM domain review — triage

Four reviewers, four non-overlapping lenses, read-only. Reports:
[R1 write path](pm-r1-write-path.md) · [R2 progress](pm-r2-progress.md) ·
[R3 intake](pm-r3-intake.md) · [R4 views](pm-r4-views.md).

**~25 findings. The four headline claims were each verified by the controller
against the source before entering this list** — none is taken on report alone.

## The one shape, found independently by all four

Every serious finding is the same defect in a different costume: **a rule
enforced at one level and absent at the level below, or a value checked in one
representation and used in another.**

| lens | the rule | where it stops |
|---|---|---|
| R1 | writes are authorized | the route resolves no viewer at all |
| R3 | imports are scope-checked | project and workstream only; their children are not |
| R2 | an open gate caps progress at 99 | the cap tests the raw value, the screen shows the rounded one |
| R4 | a failed mutation is reported | one component was fixed; twelve call sites were not |

This is now the eighth instance in three days. It is not a coincidence and it is
not carelessness — it is what happens when a rule lives in prose and is applied
by hand at each site. Every one of these was invisible to a green test suite.

## Confirmed, ranked

### S1 — `POST/PATCH /api/projects/[id]/team` mints OWNER from an unauthenticated body (HIGH)

```js
export async function POST(request, { params }) {
  return handle(async () => addProjectTeamMember(params.id, await request.json()))
}                                    // no viewer, no check
```

`addProjectTeamMember` reads `role` from the body and writes
`Membership.create({ ..., role })`. `resolveViewer` builds `ownedBusinessIds`
from OWNER memberships — so this is a direct route to business-owner authority
over any Business that owns a project. `changeProjectTeamRole` has the same
shape.

Strictly worse than FR-038 instance 2, closed this morning: that one at least
required already being a global OWNER. This requires nothing. The audit event
records it, which makes it traceable, not prevented.

### S2 — the import pipeline writes across scopes by globally-unique code (HIGH)

`classify()` passes an ownership check for `project` and `workstream` and
**none** for `workContainer`, `workItem`, `milestone`, `gate`. Every `code` is
`@unique` database-wide, so `findUnique({ where: { code } })` reaches any row in
any workspace, business or tenant, and the plan's value overwrites it — reported
by the dry run as a routine "update".

Compounded by the import routes resolving no viewer either: `workspaceId` comes
from the request body.

### S3 — 100.0% displayed with a required gate open (HIGH)

```js
if (openReleaseGates.length > 0 && percent >= 100) { percent = 99; /* + warning */ }
...
percent: clampPercent(percent)      // Math.round(value * 10) / 10
```

Raw `99.96` fails `>= 100`, so no cap and no warning, then rounds to **100.0**.
The window is `[99.95, 100)`. The file's own header says "open required gates cap
at 99"; BR-006 exists precisely to stop this. Same shape again in
`milestoneReadiness`.

### S4 — twelve mutations that cannot report their own failure (HIGH, breadth)

`await api(...)` with no `catch`, in 8 files: delete dependency, archive project
(×2), archive workspace, unlink repo, delete file, save mount, and others. A
refused server call leaves the row in place and says nothing — identical to
success. This is the `PermissionRow` defect fixed this morning at one site while
twelve others stood.

### S5 — 22 of 61 API routes resolve a viewer (HIGH, systemic)

Not a list of holes; a posture. `assertWorkspaceInScope`, the guard SEC-001
names, is called by nothing in `src/`. R1 flagged honestly that it could not
determine whether this is accepted pre-auth debt — that question needs an owner
answer, but S1 and S2 are not waiting on it: minting OWNER from an anonymous body
is categorically different from an unguarded read.

### Below the line, real but not urgent

Cross-tenant Person+email leak in `listProjectTeam.availablePeople` (same shape
as the FR-062 leak) · two cards recomputing a number the calculator computes
differently, so one screen shows 157,000 and 125,000 at once · plan `status`
fields typed `z.string()` instead of the enums, so an import can commit a status
no view understands · archived workstreams still editable in global browsers ·
failed fetches rendering as empty states in six places · silent 500-row and
200-row caps.

## Fix plan — structural first, sites second

The instinct is to patch the sites. That instinct produced this list. Order:

**W1 — stop the bleeding (S1, S2).** Both are reachable privilege escalations.
Authorize the team routes; scope `classify()`'s child matching to the resolved
workspace by construction, not by adding four more `extraConflictCheck`
callbacks — the callbacks are the pattern that failed.

**W2 — two gates that make W1's class mechanically impossible.** ✅ shipped.

1. **`route-viewer`** — a route file exporting POST/PATCH/PUT/DELETE must resolve
   a viewer. **26 baselined**; session-creation endpoints are exempt in the check
   itself rather than baselined, because an endpoint that creates a session can
   never be repaid into requiring one.
2. **`client-mutation`** — `await api(...)` must sit inside a `try` that has a
   `catch`. **8 files baselined.**

Check 11 deliberately does **not** use a proximity window. Three proximity false
positives in one day was enough — one of them changed a progress calculation. It
brace-matches the real `try` blocks and requires a `catch`, so `try { … }
finally { … }` — the original `PermissionRow` shape — is correctly reported as
unguarded. Verified by planting exactly that.

Gates before the long tail, deliberately: fixing 12 call sites by hand without a
gate means the thirteenth arrives next week.

**W3 — the numbers (S3 and the two disagreeing cards).** Cap on the value the
user will see, not the value before rounding. Delete the recomputation in the
cards and read the calculator.

**W4 — the tail.** Enum-typed plan fields, archived-entity visibility, empty-vs-
error states, disclosed caps.

**Not now:** MRP and revenue-vs-plan, both blocked on data that does not exist,
by owner decision.

## The largest item still open, stated plainly

The three `/api/import/*` routes take `workspaceId` from the request body and
resolve no viewer. They are in the `route-viewer` baseline.

S2's structural fix bounds the damage — a plan can now only touch rows inside the
resolved workspace — so this is no longer "overwrite any tenant's work". What
remains is "choose a workspace you were not given". Closing it needs a decision
nobody has made yet: import is a write, so `ownsBusiness` is the obvious bar, but
a portfolio-scoped Workspace has no Business, and what authority governs *that*
is undeclared. Guessing at it at the end of a long change is how a security fix
becomes a second incident. It needs an owner answer, then an FR.

## Prevention, stated as the rule it should have been

A guard belongs where the thing it guards is *constructed*, not at every place
the construction is used. `classify()` should not be able to match a row outside
the target workspace; a mutating route handler should not be able to run without
a viewer. Both are expressible in code rather than in review.

Where that is impossible, the rule needs a check with a shrink-only baseline —
because a rule in prose is followed exactly as often as someone remembers it, and
this document is the eighth measurement of that rate.
