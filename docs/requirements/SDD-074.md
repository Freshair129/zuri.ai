```text
| SDD-074 | Plugin auth is one canonical `/api/plugin/auth` route family over three identity-owned models (`PluginInstallation`, `PluginAuthorizationCode`, `PluginSession`), with every handler thin over `src/modules/identity/plugin-auth-service.js`. `/authorize` carries two operations for one reason: a GET that renders and never acts (it 302s to `/plugin/authorize` without reading a session or touching the database) and a POST that acts and only from that screen's own form. The consent screen's facts are server-derived through the same service functions the mint uses — `assertPluginAuthorizeParameters` for the parameters and `derivePluginCapabilitiesForViewer` for the capability list — so the screen cannot validate one request while the mint performs another. The two consent tokens are HMACs over `ZURI_SESSION_SECRET` and are stored nowhere, so the gate needs no model and no DDL. Single-use is a **database predicate, not a read-then-write**: consumption is `updateMany({ consumedAt: null })` inside the same transaction that creates the session, so two concurrent redemptions produce one count of 1 and one count of 0 and the loser throws before anything is written. The PKCE challenge is compared with `timingSafeEqual`, never `===`, because it is a secret comparison. Client configuration is read from the environment, exact and fail-closed. The plugin session is neither the browser session nor the MCP continuation id, and plugin input never authors Tenant/Business/Membership/role scope — `resolveViewer` is the only scope resolver, called without `platformGrant`. `POST /token` and `POST /revoke` are structurally exempt from the Check-10 route-viewer ratchet, the same class as the `/api/auth` lifecycle endpoints: their only credential is the one-time code or the opaque bearer, so requiring a browser viewer there would be the broken boundary, not the safe one. | FR-123; ADR-052, SEC-022, SDD-024, ADR-017 |
```
