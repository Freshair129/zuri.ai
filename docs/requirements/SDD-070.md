```text
| SDD-070 | NFR-020's per-stage counts are written by reusing `PipelineStep`'s own `actualCount`/`insertedCount`/`failedCount` columns — present since FR-071, unwritten by anything until this decision. `zPipelineEvent` gains three optional fields under the same names; `stageData()` persists them only when a caller actually supplies one, so a `STEP_HEARTBEAT` or a plain success from the Supabase migration path — every existing caller — leaves them exactly as they were, and an already-recorded count is never overwritten with an omitted one. `actualCount` is `records_in`, `insertedCount` is `records_out`, `failedCount` is `records_failed` — a field-name mapping decision, the same shape as SDD-068's `checksum`/`content_hash`. `records_quarantined` and `retry_count` are not wired to anything: BR-022's quarantine vocabulary and replay-within-run don't exist for knowledge ingestion, and a stored 0 for either would be indistinguishable from a measured zero — the exact defect found on `PipelineRun` while building this. This fix does not reach backward: every migration-pipeline run and every knowledge-ingestion run that predates this slice keeps its `@default(0)`, and `actualCount`/`failedCount` are `Int` NOT NULL with nothing correlating "never measured" — no signal distinguishes an old unmeasured zero from a new measured one. The monitor's `fmt()` already renders `null` as `—` rather than `0`; it has simply never been given a null. Closing that gap needs a migration of its own and is not this slice's to make. | NFR-020; SDD-069, SDD-066, SDD-057, BR-021 |
```
