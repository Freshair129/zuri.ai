| FR-242 | The credential vault (SecretStorePort, FR-223) generalises beyond `LINE_CHANNEL` to `OAUTH_CLIENT` (`{clientId, clientSecret}`, the ADR-053 provisioning shape) and `MODEL_PROVIDER_KEY` (`{apiKey}`), each validated against its own bundle schema and carrying the same write→activate→rotate→revoke→resolve lifecycle guarantees a `LINE_CHANNEL` credential already has — versioning, compensation on a failed follow-up, and scope re-check on every operation. A credential written under one kind never resolves as another (SEC-033), and a write that would silently change an existing connectionId's stored kind is refused (`CREDENTIAL_KIND_MISMATCH`) before any secret reaches a store, in both the envelope store and the Supabase Vault SQL layer. Neither new kind carries a provider-code allow-list or a destination concept, since ADR-053 is not yet implemented and no fixed provider list exists for model providers; `activate`/`revoke` are reused unchanged for every kind, since neither reads `secretKind`. This does not retire the Phase-1 model-credential resolver (`phase1-runtime.js`, `zuri_core.resolve_phase1_line_secret`) — a separate mechanism live production Anthropic-key resolution still runs through — which is ADR-089 §4.8 phase 7's second half, left as a distinct follow-up requirement. | 🟠 built on branch `feat/vault-provider-kinds-generalization` 2026-09-15 (ADR-089 §4.8 phase 7, TASK-ZAI-103) — `secret-store-port.js` (`BUNDLE_SCHEMA_BY_KIND`, `RESOLVABLE_SECRET_KINDS`), `envelope-secret-store.js`, `supabase-vault-secret-store.js` (`zuri_core.provider_secret_write`/`provider_secret_resolve`); migration `20260915000000_credential_vault_provider_kinds.sql`, not applied; `tests/integration/credential-vault-provider-kinds-lifecycle.test.js`, `tests/unit/integration/credential-vault-provider-kinds-migration.test.js`, extended `secret-store-port.test.js`/`supabase-vault-secret-store.test.js`; not merged, not deployed. Known residual gap: `zuri_core.channel_secret_write` (`LINE_CHANNEL`, frozen/live) has the mirror-image kind-mismatch gap in the opposite direction and is not guarded, since this migration does not edit that function's body; nothing today writes a non-LINE kind at a connectionId already provisioned for LINE_OA, but it is not structurally prevented |
