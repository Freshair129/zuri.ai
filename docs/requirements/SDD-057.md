# ZAI:SDD-057

<!-- canonical-row:start -->
```text
| SDD-057 | The seventeen-stage knowledge ingestion pipeline reuses the FR-071 execution ledger rather than declaring new models. At the storage layer that is free: `dataPipelineDefinitionId` and `pipelineStageId` are plain `String` columns with no enum, no relation and no check constraint (`prisma/schema.prisma`), so a new definition id and seventeen new `DPS-*` stage ids need no migration. At the contract layer it is not free, and saying so is the point of this decision: `zPipelineEvent` and `zPipelineRunInput` pin `dataPipelineDefinitionId` and `executionContractId` with `z.literal`, `pipelineStageId` is refined against the ten-entry FR-071 catalog (`src/platform/integrations/core/pipeline-tracking-contract.js`), and the tracking service materializes that one catalog on every run creation — so `DPL-KNOWLEDGE-INGEST-V1` is rejected today, and the first implementation slice must parameterize the FR-071 envelope by definition id before it can register anything. That is a change to implemented, tested FR-071 code, named here rather than discovered later. A second execution ledger remains the wrong answer: it would give one question two answers and make the reconciliation evidence something that has to be believed twice. `PipelineRecordEvent` already carries `docId` / `picId` / `factId` — written on every record event and read by provenance-filtered replay, with no producer supplying a non-null value today — and knowledge ingestion reuses their existing FR-071 meaning rather than redefining it. Current scope clarification (ADR-073, 2026-09-08): the contract/catalog parameterization is implemented. The prohibition is on a second execution ledger; the approved isolated slice adds seven lineage/batch/evidence/cursor/receipt models without replacing FR-071. Historical present-tense statements above describe the declaration baseline. | FR-109; FR-071, SDD-042, ADR-030, ADR-050 |
```
