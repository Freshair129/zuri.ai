| FR-130 | Business-scoped GitHub repository projection: a `Repository` a Business already owns may additionally name its GitHub origin, and a person the Business admits may read that repository's tree and file contents in the console, read-only. (a) The binding declares **no new model, no new column and no migration**, because the entity already exists: FR-008 created `Repository` and FR-073 made it owned by exactly one Business, which is the scope CR-004 also chose and the only scope the viewer contract can govern (SDD-037). CR-004's `githubRepoUrl` is `Repository.url` beside `ownerName`/`repoName`/`fullName`/`provider`; its `githubBranch` is `Repository.defaultBranch`, with `ProjectRepository.branch` as the per-link override; GitHub's numeric repository id is `Repository.externalRepoId` mapped through `ExternalEntityRef` — the identifier BR-002 names by example ("GitHub id") and forbids as a key; and CR-004's three sync fields are **not stored at all**, because they are artifacts of a design this one does not adopt: `lastCommitSha`, `lastGithubSyncAt` and `githubSyncStatus` describe a mirror kept in step with an origin, and a read-through projection (d) keeps no mirror — the commit a reader is looking at comes from the same live fetch that produced the tree, so storing it would be a second answer to a question the response already carries. Should a cache ever be added, the watermark is `SyncCursor.cursorValue` with `lastSuccessAt` beside it and `IngestionRun.status` for the outcome, and that is the point at which its keying must be settled rather than assumed: `SyncCursor` is unique on `(connectionId, resourceType)`, so one connection covering several repositories has no per-repository cursor without either compounding `resourceType` or narrowing a connection to one repository — and `externalAccountId` names an *account*, which is why `Repository` is a separate model in the first place. Five columns on `Business` are refused: `Business` is a scope-chain entity, columns on it would cap a Business at one repository where `Repository` already permits many, and a foreign URL and commit SHA on a core scope row is the shape BR-002 exists to prevent. (b) A private repository's credential is an `IntegrationCredential.secretRef` on a `github` `IntegrationConnection`, resolved through the `SecretManagerPort` — a reference, never material, never in a browser response (SDD-043, SEC-015). Registering the provider row is idempotent on its code and needs no migration. (c) Push delivery is an **FR-081 adapter, not a new endpoint**: a webhook is one of the four `SOURCE_TYPES` that requirement already names, and a bespoke `/api/webhooks/github` would be the second raw-write path FR-081 forbids by name — the same finding CR-005's LINE connector drew. The tenant CR-004 omits is never read from the payload: the delivery's `installation.id` selects exactly one `IntegrationConnection` on `(providerId, externalAccountId)` and **zero or multiple candidates fail closed** (the FR-079 rule), the connection carries the trusted `tenantId`/`businessId`, and `repository.id` then resolves to a `Repository` through `ExternalEntityRef`. The authentication CR-004 omits is GitHub's `X-Hub-Signature-256` — HMAC-SHA256 over the raw body under the connection's webhook secret, constant-time compared, verified before anything is parsed for meaning or written; routing reads `installation.id` only, which is a non-secret selector the signature then proves, so trust follows verification rather than preceding it. (d) **File content is never persisted** — only push metadata converges on the raw substrate, and the tree and blob reads that render a file are read-through with no row of their own (SDD-076). Writes to `Repository` continue to go through project-manager's `repository-service`, which stays its only writer; this requirement reads that model and does not claim it. (e) The projection is bounded by a declared path scope, deny-by-default in the shape SEC-009 already uses, and `vaults/`-class live database state is excluded rather than discovered by a previewer (CR-006 §5.2). No file tree UI, purpose badge, multi-format previewer or metadata panel is in scope: CR-004 §2.B is a four-part feature programme, not this requirement. Reworked from CR-004 | 🟠 partial (2026-08-30) — the one part of this requirement that was never behind the blocker is closed; everything the requirement is actually about remains **blocked, not merely unbuilt**, on one named thing that is not effort: nothing in this repository can determine whether an arbitrary bound repository contains personal data, and there is nowhere to record the assertion that it does not. SEC-005 consent attaches to an FR-023 `Customer` row per Business (SDD-053) and FR-022 erases through `Person`/`Customer`; a spreadsheet inside a repository has neither, so a projection over it would be a second way into personal data that reaches none of the controls governing the first way. CR-006 establishes this is not hypothetical — the very repository CR-004 names held customer contact lists, quotation reports and per-customer purchase history tracked in git on a public remote, and `git status` reported nothing wrong throughout — and remediating that instance does not lift the blocker, because the next bound repository has the same unverifiable property. What is missing is an attestation shape and an authority to make it: who may declare a path scope free of personal data, and what is recorded when they do. That is a product and data-protection decision nobody has made. No attestation shape was invented in the meantime, and that is a decision rather than an omission: FR-129's parallel does not hold, because there the column existed in the schema and in production DDL and only its writer was missing, whereas here there is no column, no row to attach an assertion to, and no policy for who may make one — `AuditEvent.action` is a plain `String` so a value could be written, which is the trap rather than the answer, because a free string nothing validates and no rule governs is displayed as a control while being a note. **What is closed** is the false green the catalog carried beside it: `src/platform/integrations/core/connector-catalog.js` now derives every connector tile's state from the `listPhase1Integrations` read model the same page already renders, and a catalog entry can no longer carry a state at all. Four entries had been hardcoded `CONNECTED` — LINE OA, OpenRouter, Vercel Ingress and GitHub — and two of those four have no connector anywhere in `src/`, so no configuration could have made them true; a fifth, Google Gemini, was wrong in the other direction, reading `AVAILABLE` for a provider in `PUBLIC_LINE_PROVIDERS` that the Phase 1 model form could always connect. `AVAILABLE` is not replaced by a friendlier synonym: `CONNECTOR_NOT_IMPLEMENTED` and `NO_CONNECTION_RECORDED` keep apart the two different facts it had merged, a row arriving without computed health resolves to `NOT_CONNECTED` rather than inheriting green, and the dead "Connect" control is gone from an entry with nothing to connect, because a button that does nothing is the same claim moved one element to the right. Secondary and still open: `DATA_LANES` has no value a source repository honestly belongs to, and inventing one is the ADR-038 decision made once for market evidence, not a free enum edit |
