| FR-129 | Catalog publication approval gate: a `DPL-SUPABASE-BUSINESS-KNOWLEDGE-V1` run that has produced a candidate projection does not reach `DPS-PUBLISH` until an authorized human has recorded an `APPROVED` `PipelineGateDecision` against that run, and a `REJECTED` decision sends it to `DPS-ROLLBACK` instead — the two stage labels FR-071's catalog has always carried ("Publish approved projection", "Rollback failed or rejected run") with nothing yet deciding which one a run takes. (a) The decision is recorded on the existing FR-071 execution ledger and declares **no new model and no new column**: `PipelineGateDecision.decidedByPersonId` is who signed, that row's own `createdAt` is when, `required` is whether the gate was waivable, `reason` carries a rejection, and `PipelineRun.artifactRef`/`artifactSha256` already identify the artifact the run applied. A second run table as CR-003 proposes is refused: `IngestionRun` (FR-081) is acquisition evidence for one connection and `PipelineRun` (FR-071) is the execution ledger for one pipeline definition, and a third answer to "what happened in this pipeline" would make the reconciliation evidence something that has to be believed twice (SDD-057). (b) The evidence a reviewer acted on — the candidate publication's own identity, and the added/changed/unchanged counts shown — is written to `PipelineGateDecision.evidenceJson` (SDD-075); a signature whose evidence is empty records that somebody approved but not what they saw, which is not an auditable decision. (c) The destination vault is not stored: it resolves from the run's Tenant/Business scope through API-010 (FR-057, ADR-022), so a stored copy would be a second answer to which vault a scope maps to. (d) Tier 1 records and does not execute (ADR-043 D2.1, ADR-050 D3). The gate is therefore a precondition the executing worker must observe and the ledger makes checkable afterwards — a run whose publish stage succeeded with no prior `APPROVED` decision is a detectable violation — not an interlock this repository enforces on a worker it does not run. (e) **Distinct from FR-110's Stage 17 quality gate**, permanently and by design: FR-110 is an automated `PASS`/`PASS_WITH_WARNINGS` verdict on a `DPL-KNOWLEDGE-INGEST-V1` knowledge snapshot, this is a human signature on a business-knowledge catalog version, and both will answer to "approval gate on a pipeline run" in any future search while sharing the one `PipelineGateDecision` table. Reworked from CR-003; no reviewer UI is in scope (CR-003 §2.B is a feature programme, not this requirement) | 🟠 partial (2026-08-30) — the record and the check are built; the signing surface is not, and no migration, model or column was added. `zGate` now carries an optional `.strict()` `evidence` member (`catalogVersion`, `artifactSha256`, `addedCount`, `changedCount`, `unchangedCount`) that an `APPROVED` decision on **this** definition may not omit — scoped to the definition and not to the shared table, so FR-110's Stage 17 gate is unconstrained; `recordPipelineEvent` persists it to `evidenceJson` and `gateSummary` returns it, closing SDD-075's "present, tested for existence, and unreachable" gap end to end; (2) is stated as validation too — an `APPROVED`/`REJECTED` decision must name a `decidedByPersonId` and a `REJECTED` one a `reason`, said in the envelope because the column is `String?` with no `Person` relation and cannot say it. (d) is answered on the response it names: `GET /api/pipelines/runs/{executionRunId}` returns `gateCompliance` beside `gates` and `steps` — computed server-side over every step row, because that response's step-side field is `stageTimeline` (`latestByStage`, one row per stage) and `(runId, pipelineStageId)` is not unique (SDD-071), so a second unapproved publish row is invisible to a reader of it — reporting every `DPS-PUBLISH` step that SUCCEEDED with no **prior** `APPROVED` decision as a `PUBLISH_WITHOUT_APPROVAL` violation and carrying `enforced: false` because this tier detects and does not prevent — an approval recorded *after* the publish is reported, which is the case an existence check reads as compliant. **No route that creates an `APPROVED` decision is exposed**, deliberately: the authorization policy such a route would implement is the blocker, and shipping it under scope-level admission alone would make "any member of the run's Business may sign a catalog publication" the product's policy, chosen by omission and cheaper to add later than to narrow. Still blocked on that unmade product decision — who may sign, and whether a gate is required per definition or per run; because "required" is undecided the detector does **not** read `WAIVED` as satisfying the gate, and names every observed gate status in the finding instead. `PipelineReconciliation.evidenceJson` is still written as `'{}'` and is left visible as its own finding rather than half-closed here |
