```text
| FR-122 | A Profile states who the person is, not just what to call them: FR-066's Profile step requires **given name, family name and telephone number**, over the display name it already collected and the optional email it already carried. Display name stops being something the person types twice — it is supplied by them or defaulted server-side from given + family name, never left empty, because `Person.displayName` is what every existing surface renders. The three new fields are stored **nullable on `Person`** and required **at the profile boundary instead**, and the distinction is load-bearing rather than a convenience: `Person` rows already exist that can never satisfy them — `prisma/seed.js`, FR-107's operator bootstrap, and above all every Person that FR-023's LINE ingest creates on first contact, which is created from a `lineUserId` and has no name or telephone number to give. A database-level requirement would make those rows unwritable and take the LINE intake surface down with it; the profile step is the only place a person states these things themselves, so it is the only place the requirement can be honestly enforced. Profile remains an identity step over `Person`, never an authorization grant (FR-066, BR-016). | ✅ implemented |
```
