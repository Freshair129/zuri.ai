| SEC-022 | Plugin auth is a separate public-client boundary: no password or browser cookie enters the plugin; authorization codes are PKCE S256-bound, single-use and stored only as hashes; access tokens are opaque, 15-minute and hash-stored; a replayed code is refused **and** revokes the session it already minted (RFC 9700 §4.1.1); revocation is idempotent and answers identically whether or not the token existed; client id, redirect URI and installation are allow-listed exactly with no host normalization; every capability and scope decision comes from the trusted Zuri identity resolver, without a platform grant. All four responses are `Cache-Control: no-store`, and no error echoes a raw code, token or internal message. Authorization now requires consent that was actually given: `GET /authorize` renders a screen and mints nothing, and minting requires a POST carrying all three of the session cookie, a session-bound anti-CSRF token and an HMAC-signed request token that is the sole source of the parameters acted on, with a 5-minute TTL and every field re-validated against live configuration on approval. The anti-CSRF token is redundant with `SameSite=Lax` today and is kept so the defence does not live entirely in a cookie attribute another change could remove silently. Refusal is available and answered as `error=access_denied` with the original `state`. Expired codes and sessions have a locally tested maintenance service that retains each code while an unrevoked, unexpired linked session can still be revoked on replay. Production maintenance invocation, client registration, device-binding evidence and security sign-off remain outstanding. | FR-123 / ADR-052 security gate — 🟠 consent closed; production activation gated |
