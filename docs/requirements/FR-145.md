| FR-145 | Supabase pooler MODE follows deployment topology, not a fixed default (ADR-058 D9): `resolvePoolMode(env)` (`src/lib/db.js`) picks Supavisor SESSION pooling (port 5432, no `pgbouncer` param) for a long-running process and TRANSACTION pooling (port 6543, `pgbouncer=true`) only when `VERCEL` is set, so a single container gets a small stable connection count and one Postgres round trip per query instead of paying a transaction-mode backend checkout on every query it never needed; `ZURI_DB_POOL_MODE=session\|transaction` is an explicit operator override for a topology neither branch guesses (e.g. several container replicas sharing one Postgres, which still needs transaction-mode safety). Applies only to a `*.pooler.supabase.com` host — a direct connection or non-Supabase Postgres passes through untouched. | 🟠 implemented 2026-09-04 — `src/lib/db.js`, `tests/unit/db-runtime-config.test.js` (12 cases incl. the FR-145 group); measured against the production Supabase project from the Docker deployment (ADR-058): the same host, a warm connection pool, transaction mode cost ~650-750ms per trivial query with no improvement across repeated calls, session mode ~130-145ms — matching raw TCP RTT. Docker Compose defaults to session mode with no operator action; Vercel behavior is unchanged |
