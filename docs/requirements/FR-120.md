| FR-120 | Self-serve account creation: an unauthenticated visitor creates their own `Person` and `PersonCredential` at a public `/signup` (`POST /api/auth/signup`) and continues into FR-066 at its `PROFILE` step. This closes the product's only door. FR-066 begins *"after a provider-neutral local identity/session exists"* and never says how one comes to exist; FR-067's invite is accepted as `acceptWorkspaceInvite({ token, personId: viewer.principal.id })`, so it attaches membership to somebody already authenticated and cannot admit a stranger; and the only writers of a credential are `prisma/seed.js` and FR-107's operator bootstrap, which is operator-run and refuses an existing credential (409). Nobody new can enter — which also means nobody new can be invited, because an invite needs a Person to attach to. **Signup itself confers no authority**: it creates no `PlatformGrant`, no Tenant, Business, Space or Project, and no `WorkspaceMembership`. What the new Person may do next is exactly what FR-066 already grants any profiled Person and no more — the owner path of `createOnboardingWorkspace`, which creates one `Portfolio` plus one OWNER `WorkspaceMembership` over it and, by AC-066.2, zero Organization/Tenant/Business/Space/Project rows. Signup therefore widens who can reach that path; it does not widen the path. Entry to an existing team remains FR-067's invite, and the resting state for a Person holding nothing is FR-066's Waiting Room. Signup never overwrites an existing `PersonCredential` — the same refusal FR-107 makes, for the same reason. Password validation and hashing are the FR-046/FR-104 path's `hashPassword`, called rather than copied, so a policy change cannot apply to one door and not the other; the human `PSN-` code comes from the same `uniqueHumanCode` generator (BR-002); and the session is FR-046's minting path, not a second implementation. **The caller is signed in on success** rather than returned to `/login` to retype the password they just chose, and the cookie is a browser-session cookie — signup carries no "remember me" tick, so it takes AC-046-15's default rather than opting itself into seven days. Creation writes an audit event. Identity stays provider-neutral and local: no SSO or third-party provider is in scope. **Email is an identifier here, not a channel.** This installation has no mail transport — the stated reason FR-104 has no public forgot-password — so there is no verification step and no "check your inbox" response to hide a taken address behind. A taken email therefore returns a distinguishable error instead of stranding the caller in silence. That enumeration is accepted deliberately: with no mail the alternative is a signup that fails invisibly, and learning that an address holds an account grants the learner nothing, because that account carries no scope, no capability and no membership until its holder creates a Workspace or an owner invites them. The compensating controls are the audit trail and a per-source rate limit — and that limit is **in-process and per-instance**: a fixed window held in the Node process's own memory, which resets on restart and does not span replicas. Stated rather than glossed, because a control described more strongly than it is built is worse than one described honestly. An unverified address must never be treated by any later requirement as proof of contact. | ✅ implemented 2026-08-29 — `/signup`, `POST /api/auth/signup`, `signup-service.js`, `signup-rate-limit.js` and `signup-copy.js`; 47 unit tests across four new files, one more added to the entry-surface boundary suite, and 7 e2e. Two limits are recorded in the feature note rather than left for a reader to discover: `Person.email` carries no unique index in either schema, so the taken-address refusal is a check inside the transaction and not a constraint (the index is a migration against live data and is named as owed, not smuggled in); and the rate limit is in-process, per-instance and keyed on a client-supplied forwarded header, which makes it a speed bump against a naive scanner and nothing against a deliberate attacker — the audit trail is the control this leans on. `authenticateUser` gained one additive lowercased-email arm, without which signup would have created accounts whose owners could not sign in with the casing they typed |
