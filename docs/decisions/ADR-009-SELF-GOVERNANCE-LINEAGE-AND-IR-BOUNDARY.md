# ADR-009 — Self-governance: doc-graph lineage, the IR boundary, and dogfooding the PM

**Status:** Accepted
**Date:** 2026-08-13
**Decided by:** Owen (owner)
**Relates to:** [ADR-003](ADR-003-V2-REPLACES-V1-BY-REUSE.md) (reuse, one-directional), [ADR-004](ADR-004-DOCUMENTATION-ARCHITECTURE.md) (doc architecture), [ADR-007](ADR-007-LINE-AI-STACK-SEQUENCING.md) (LINE/AI knowledge stack), [ADR-008](ADR-008-BUSINESS-CENTRIC-SHELL-AND-SCOPE-LENS.md), AGENTS.md §18–19 (id contract, annotations)

Records a set of architecture decisions worked out while deciding whether to build our own
lineage/dependency tooling or reuse GoVibe. Written so these choices live in a document, not
only in a conversation — the exact drift ADR-008's process was meant to close.

## Context

GoVibe (`G:\GoVibe`, read-only reference here) is an agent-swarm project manager for *building
apps*. It has: **Deep Scan** (`govibe-core/src/scan/` — 12-stage decomposition → observed graph
→ GKS canonical truth), a **Mission Control** cockpit (AST Explorer, Graph Studio, Cytoscape
call-graph, ERD), and its own doc governance. RWANG runs on GoVibe only as a *thin overlay*
(its OPERATING_AGREEMENT forbids dueling registries).

Zuri already ships a **Project Manager** domain (WBS: Project → Workstream → WorkContainer →
WorkItem, plus a generic typed `Dependency` model), a **doc-graph + preflight** governance layer
(headed "RWANG doc-preflight"), and a **knowledge projection** for the agent (ADR-007 P5). The
question was what to build vs reuse. The answers below draw the lanes.

## Decision

### D1 — Three systems, three lanes, no overlap
| System | Lane | Coupling |
|---|---|---|
| **GoVibe** (owner-operated; read-only to agents here) | **Deep Scan** → code dependency map (observed candidates), Mission Control visualisation | One-time bootstrap; **never a live Zuri dependency** |
| **RWANG** — in Zuri = `scripts/doc-graph.mjs` + `scripts/doc-preflight.mjs` | Doc-architecture / governance: requirement↔code↔test wiring, coverage, **lineage**, CI guard | In-repo; Zuri self-verifies in its own CI |
| **Zuri Project Manager** | Human dev project tracking (WBS + `Dependency`) | Ingests via the envelope; **no code scanning** (that is GoVibe's lane) |

### D2 — Zuri's intermediate representations (we do NOT build a GoVibe-style code semantic IR)
- **Governance IR** = `docs/.doc-graph.json` — nodes (document · ADR · requirement · code_file ·
  test) + edges (`implements` · `verifies` · `follows` · `specifies` · lineage). Regenerated from
  the filesystem, never hand-authored.
- **Write IR** = the intake **PlanEnvelope** (`contracts/plan-envelope.schema.json`). Every
  ingestion normalises to it → validate → semantic check → dry-run → single transaction → audit
  (BR-009, SDD-009). This *is* Zuri's canonical "semantic IR" for data-in.
- **Knowledge projection** (ADR-007 P5, FR-024) = the agent-facing read model.
- A **code-symbol semantic IR** (GoVibe GKS: functions/classes/call-graph) is **out of scope**.
  It comes from scanning; if symbol-level detail is ever needed, import GoVibe's scan output once.

### D3 — Typed lineage edges in the governance IR
`doc-graph.mjs` parses document control blocks — `**Supersedes:**` / `**Superseded by:**` /
`**Relates to:**` — into typed edges:
- `supersedes` (newer → older) answers **"what replaced what"**.
- `relates` answers **"where did this come from"** (provenance / derivation).

Preflight guard (`lineage`): a doc marked superseded must carry an incoming `supersedes` edge,
so an orphaned supersession ("replaced by *what*?") is a warning, not an invisible gap.

### D4 — "symbolLink" already exists as annotation edges
GoVibe's `symbolLink` (task → code symbol, from a scan) is, in Zuri, the `@req` / `@spec` /
`@tested` annotations resolved into `implements` / `verifies` / `follows` edges — at **file**
granularity, **authored, no scan** (consistent with D1). Already documented in CLAUDE.md
("Doc-code annotations") and AGENTS.md §18–19. The importer (D5) carries these onto each WorkItem.

### D5 — Dogfood: Zuri's own roadmap is a project inside Zuri's PM
Zuri's ADRs / FRs / modules and their supersede·derive lineage are **imported into Zuri's own
Project Manager** (a self `PRJ-ZURI-V2` project) through the envelope pipeline (D2) — so they
render on the existing **WBS** + **/dependencies** views. Generated by `scripts/self-plan.mjs`
(doc-graph.json → PlanEnvelope), committed via the existing import pipeline, human-maintained
after import; re-running refreshes from the graph. This makes the PM real (it must be built
anyway) and yields the lineage view for free — no bespoke viewer.

## Consequences

- New: `scripts/self-plan.mjs` (governance IR → write IR), imported via the existing pipeline.
- **No schema change**; **no runtime dependency on GoVibe**; Zuri CI stays self-contained.
- Scanning stays out of Zuri; GoVibe's Deep Scan is an optional, owner-run, one-time bootstrap.
- These decisions now have a documented home, so the doc-graph has a truth to diff against —
  closing the "decisions lived only in chat" gap.
