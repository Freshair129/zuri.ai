# ZV2-CR-007 — Interface Inventory normalization and responsibility split

## Authority

This CR follows ADR-004 D10: cross-cutting documentation changes that require an explicit migration or retirement inventory live under `docs/changes/ZV2-CR-*.md`.

## Change summary

Normalize `docs/INTERFACE-INVENTORY.md` so it has one primary responsibility:

> **Canonical registry of user-visible interfaces and their implementation status.**

The current document mixes interface inventory with shell architecture, route sitemap, feature inventory, API inventory, documentation audit, implementation evidence, change planning, and owner-decision history. Those concerns already have or should have separate authoritative homes.

This CR does not redesign the UI, navigation, shell, routes, or Design System. It changes documentation ownership and removes duplicated facts that can drift.

## Execution status

The normalization has now been applied to docs/INTERFACE-INVENTORY.md:

- one registry row exists for each of the 37 current page routes;
- the Business Home shell slot is explicitly separated from the seven
  operational domain keys and 21 operational sub-domain entries;
- /files, /platform/integrations and /projects/[projectId]/inventory are represented;
- API endpoint catalogs, generated feature counts, change DAGs and owner
  follow-up ledgers have been removed from the canonical inventory and replaced
  with authority links;
- machine-checkable route/domain count markers are guarded by
  scripts/doc-preflight.mjs.

docs/appendices/A-api-spec.md was also normalized to declare 63 current API
route handlers, separate the five deferred integration lifecycle paths from
current routes, and state the minimum endpoint contract fields.

The documentation migration is complete in the working tree. The final
governance exit gate remains pending while the concurrent FR-076/FR-077 session
owns dirty route, feature, schema and generated-output changes.

## Problem statement

`INTERFACE-INVENTORY.md` currently identifies itself as both **Interface Inventory and Shell Boundary** and declares a scope covering entry, shell, domains, sub-domains, Project resources, content, indicators, and API contracts.

It also contains sections for:

1. canonical shell hierarchy;
2. logical layout architecture;
3. page/route inventory;
4. component/content building blocks;
5. domain/sub-domain inventory;
6. feature inventory;
7. route-state inventory;
8. API/interface inventory;
9. documentation coverage audit;
10. proposed change DAG; and
11. owner decisions/follow-up.

This makes the file a combined registry, architecture note, audit report and change ledger rather than a bounded interface inventory.

## Evidence of drift and ambiguity

### E1 — Page-count inconsistency

Section `2.1` is titled `Page routes (35 page files)` while the table total is `34`.

A canonical inventory must not carry two counts for the same set.

### E2 — Business Overview classification is internally ambiguous

The document states that `/overview` is the BusinessShell root and **not a Development sub-domain**, but later feature wording says FR-044 includes **Business Overview as the first Development sidebar entry**.

`ROUTES-SITEMAP.md` is clearer: Business Overview is the shell root, while the Development sidebar list contains the seven Development capabilities.

The Inventory should consume that classification, not independently reinterpret it.

### E3 — API inventory duplicates the API authority

Section 6 inventories API handlers and endpoint contracts even though `docs/appendices/A-api-spec.md` is the API inventory authority and `ROUTES-SITEMAP.md` already points to it.

### E4 — Feature inventory duplicates generated traceability

Section 4 summarizes FR coverage and counts even though `FEATURE-MAP.md` is generated by `npm run docs:graph` and exists specifically to avoid a hand-maintained duplicate index.

### E5 — Change planning is embedded inside a current-state inventory

Sections 8 and 9 include a proposed change DAG, implementation sequencing and owner follow-up decisions. This couples the inventory to one historical change slice and makes it age as the implementation advances.

## Decision requested

Approve the following document responsibility contract.

### 1. `INTERFACE-INVENTORY.md` owns the interface registry

It SHALL answer:

- What user-visible interfaces exist?
- What is each interface for?
- Which route exposes it, if routable?
- Which shell contains it?
- Which domain/sub-domain or resource context owns it?
- What are its primary visible content blocks and user actions?
- Which important UI states must the interface expose?
- What is its implementation status?
- Which specs/decisions and implementation files prove it?

It SHALL NOT become the authority for route hierarchy, domain navigation, API contracts, feature coverage, Design System rules, or change sequencing.

### 2. `ROUTES-SITEMAP.md` owns current route-to-shell topology

Route hierarchy, nested layouts, route families and shell placement remain authoritative there.

The Interface Inventory references routes but does not independently maintain a second route tree.

### 3. `SITEMAP-DOMAIN-NAV.md` owns domain/sub-domain information architecture

The Interface Inventory records the domain/sub-domain assignment of each interface but does not redefine the navigation model or future reserved domain surface.

### 4. `UI-DESIGN-SYSTEM.md` owns presentation/component rules

The Interface Inventory may list components or patterns used by a surface, but token rules, typography, spacing, component states and accessibility contracts remain in the Design System.

### 5. `FEATURE-MAP.md` owns generated feature traceability

The Interface Inventory may reference FR ids relevant to a surface. It must not duplicate global FR counts or generated code/test coverage tables.

### 6. `appendices/A-api-spec.md` owns API inventory

The Interface Inventory may reference an API dependency when it materially explains an interface, but endpoint catalogs and handler counts must remain in the API specification.

### 7. ADR / CR / RCA own decisions and change history

- ADR: architectural decision and durable rationale.
- CR: proposed bounded change, migration and acceptance criteria.
- RCA: incident/root-cause and prevention.
- Interface Inventory: current interface registry.

Historical change DAGs and owner-decision ledgers shall not live inside the canonical Interface Inventory.

## Target Interface Inventory schema

Each routable or materially distinct user-facing interface SHOULD have one registry row or record with the following fields:

| Field | Purpose |
|---|---|
| Interface | Stable human-readable interface name |
| Route | Route/path when routable; `N/A` for embedded surfaces |
| Shell | EntryShell / BusinessRoutingShell / BusinessShell / ProjectResourceShell / other approved shell |
| Domain / context | Domain, sub-domain or opened resource context |
| Purpose | User outcome supported by the interface |
| Primary content | Main visible information blocks |
| Primary actions | User actions available from the surface |
| Required states | Loading / empty / error / offline / forbidden / etc. where applicable |
| Access boundary | Viewer/Business/domain/resource requirement at a descriptive level |
| Status | implemented / partial / reserved / deprecated |
| Spec refs | FR / SDD / ADR / sitemap references |
| Implementation evidence | page/layout/component paths or generated evidence links |

A separate shell registry MAY remain at the top if it is bounded to interface containment and does not duplicate the architectural rationale from ADRs.

## Non-goals

CR-007 does not:

- redesign Zuri navigation;
- add or remove application routes;
- change shell behavior;
- change domain/sub-domain decisions;
- alter Design System tokens or component styling;
- change API contracts;
- create new product features;
- convert the Interface Inventory into another generated `FEATURE-MAP` equivalent.

## Exit gate

CR-007 is complete only when a reader can open `INTERFACE-INVENTORY.md` and answer **“what interfaces exist and what is their current status?”** without also having to interpret a historical implementation plan, duplicated API catalog, duplicated feature coverage report, or competing navigation authority.
