# LINE metadata-only ProductMaster disclosure from managed uploads

## Intent and authority

The owner directly approved extending the existing default-off LINE customer-product disclosure with a metadata-only `ProductMaster` source path. This proposal pins the candidate contract for independent review against the requested base `08ecc44ee7dadd41a63abb0a051cab8df5d981f9`. It does not edit canonical records, issue an ID, create a disclosure grant, report implementation or activate production.

The extension reuses the existing owner-controlled per-product/per-field preview and approval flow. It makes a narrowly typed generic managed-file source eligible beside the existing PCAT source. Only published, receipt- and manifest-backed `ProductMaster` records with an explicit exact mapping to one live Product in the same Tenant and Business can be previewed. The owner selects the existing public metadata fields and approves the exact preview. The mode grants no price or stock access and leaves FR-291's commercial eligibility unchanged.

## Inspected baseline and gaps

- The approved [LINE customer-product disclosure contract](line-customer-product-disclosure-20261024.md) is version 0.3.0. The current FR-079/FR-235 migration ties the real-product source to PCAT assets; FR-079 and FR-235 already carry the default-off, owner-approved descriptive mode and its exact Product/source binding.
- Ordinary managed uploads use the shared File Management path and receive a `FIL` human code. That code is a locator, not authority. The existing Knowledge admission service accepts `FILE` sources and only treats JSON as structured when the caller selects the existing `SMARTGIFT_CATALOG_V1` adapter. A generic text/Markdown upload, an untyped file, or a `FIL` code alone is not a ProductMaster source.
- The existing LINE disclosure candidate/reader currently filters to PCAT asset identity and validates the exact structured ProductMaster record, current corpus manifest/receipt, asset bytes, live Product, and owner policy. The source discovery path therefore does not surface an otherwise eligible ProductMaster record admitted from an ordinary managed FileAsset.
- FR-173 covers authorized source admission, durable 17-stage work and publication manifests, but it does not provide an owner-scoped retry for the terminal Stage 16 `BENCHMARK_NO_APPLICABLE_QUERIES` case. The current generic FR-071 replay route requires installation-operator authority. The existing full-run replay precedent creates an immutable child PipelineRun and new stage attempts against the same raw/parsed lineage; it is not a Knowledge-owner retry surface.
- ADR-072 phases 0–4 keep ordinary admission within the existing service and do not approve a new generic parser, direct untyped catalog/JSON path, OCR, external fetch or publication shortcut. This proposal keeps structured records on the existing FR-187 / ADR-075 `SMARTGIFT_CATALOG_V1` adapter and uses the ordinary managed FileAsset only as the immutable byte source.
- FR-291 remains the separate authority for deterministic stock and price facts. A ProductMaster metadata approval neither satisfies its TEST ONLY product eligibility nor creates a price receipt, stock permission, price permission, quote or commercial answer.

## Bounded source and disclosure contract

1. Keep the current `GENESISRAG17_CUSTOMER_PRODUCTS` mode default-off and confined to its existing verified main-dev profile and server-side Tenant, Business, LINE account, origin, installed model and no-Business-key guards. Keep the current Server/Runtime, signed-event, account, owner and final-send revalidation boundaries.
2. Add no upload route, file model, source format, corpus, policy table or second catalog. An eligible generic source must be an active same-Business managed `FileAsset` admitted as a `FILE` source with the existing `SMARTGIFT_CATALOG_V1` structured `ProductMaster` descriptor. The current corpus manifest and publication receipt must bind the source/ingestion, source version, content hash, file id/version/SHA-256 and exact record descriptor. PCAT remains eligible under its current rules. A generic file that is not an exact typed `ProductMaster` record is ineligible.
3. A `FIL` asset code, file name, title, external ID, SKU text or search rank is never a grant or identity map. A generic record is eligible only when the existing typed record maps to one active live Product in the same Tenant/Business: `record.provenance.upstreamRecordId === liveProduct.id` and `record.externalId === record.code === liveProduct.code`. Owner selection cannot remap a record that fails either equality. The existing PCAT path keeps its current Product identity rules. Ambiguous, duplicate, missing, stale, revoked, cross-scope or changed-byte bindings fail closed and require a fresh preview/approval.
4. Reuse the existing per-account owner UI. The owner chooses the Product, exact source record and fields, sees the exact values and fixed-renderer example, then approves. Preview is non-granting. Only the existing fixed metadata whitelist can be selected: live Product SKU and base unit; ProductMaster Thai/English name, category, product family, dimensions and unit weight. Missing values are unavailable. Costs, sell prices, price tiers, discounts, margins, supplier/provenance fields, stock, customer/order-specific fields, arbitrary text and all unlisted fields are not selectable and never enter the model packet.
5. At query time, policy-approved `sourceId` values constrain retrieval before corpus querying. The reader rechecks manifest, receipt, source/ingestion and exact record bytes/descriptor, current Product/Business/account binding, owner policy and selected-field projection before and after generation and at the final send fence. Raw file text, unselected fields and provenance are not answer material. Existing strict fact-ID selection and fixed Thai rendering remain in force; no broad-corpus, fixture or business-knowledge fallback is added.
6. The descriptive path grants no stock/price permission, performs no inventory or pricing read, creates no synthetic price/stock receipt, and never routes a customer metadata turn into FR-291. Stock/price intent remains under the current deterministic FR-291 parser, exact TEST ONLY allowlist, quantity/unit checks and existing owner readers. FR-291's identity, subject anchor, eligibility and status remain unchanged.

## Bounded failed-admission retry under FR-173 / FR-071

The demo failure is specific: a generic admission reached Stage 16 and terminally failed with `BENCHMARK_NO_APPLICABLE_QUERIES`; an operator has prepared the benchmark with the expected applicable sections, but a replay must still prove current applicability at Stage 16 and may fail there again. No owner-executable Knowledge retry is present. Preserve the current admission contract and add only this recovery path:

- A currently authorized same-Business OWNER may request retry only for that terminal Stage 16 `BENCHMARK_NO_APPLICABLE_QUERIES` failure while the original source, exact Tenant/Business scope, lease state, and FileAsset id/version/size/hash and bytes still revalidate. Operator benchmark correction is preparation for a successful replay, not a retry API assertion or gate bypass: the child executes Stage 16 against the current benchmark and may fail there again until its exact applicable sections match.
- Reuse the existing `KnowledgeIngestion` row and exact `sourceId`, `sourceKey`, `sourceVersion`, `contentHash`, FileAsset identity and raw/parsed artifacts. Do not append a synthetic source-version suffix, allocate a new source key, or create another KnowledgeIngestion row.
- In one guarded operation, compare-and-swap that existing row from `FAILED` to `QUEUED`, point it at an immutable FR-071 `FULL_RUN` child PipelineRun with `replayOfExecutionRunId` set to the original run, and write an AuditEvent that binds the child to its parent. The new PipelineRun and stage-attempt rows are append-only; the failed parent run and its stage evidence stay unchanged. A bare status reset, delete/recreate or history rewrite is prohibited.
- Keep the public FR-071 replay route installation-operator-gated. The retry is authorized by the current Knowledge owner scope and implemented behind the Knowledge admission surface; a Business OWNER does not gain installation-operator or generic pipeline mutation authority.
- The retry executes the normal 17-stage flow. A source becomes searchable only after the new child has the normal successful stage evidence, Stage 17 gate, publication receipt and atomic corpus-manifest update. A still-inapplicable benchmark may fail Stage 16 again; changed file, stale scope, live lease, wrong actor, concurrent retry or publication failure returns a bounded denial/conflict and preserves the prior run evidence. Retry never fabricates a Stage 16 pass or bypasses Stage 17 publication.

## Acceptance and limits

- Existing PCAT owner preview/approval and runtime behavior remains valid; a generic source appears only when its current publication evidence and typed ProductMaster record pass every gate.
- The exact record maps to exactly one live Product in the same Tenant/Business. `FIL` code or matching text cannot map it. Changed FileAsset bytes/version, record identity, source/ingestion, receipt, manifest, Product binding or owner policy prevents preview approval or runtime disclosure until a new preview is approved.
- The owner can select only the metadata whitelist above. Captured model input and LINE output contain selected exact metadata values only; no price, cost, stock, private fields, unselected values, raw source bytes or provenance. Invalid model output cannot add prose or values.
- Stock/price questions retain current FR-291 behavior, exact TEST ONLY eligibility and deterministic no-model guards. This proposal causes no stock/price reads or receipt creation and does not make real products eligible for FR-291.
- A retry test must show the Stage 16 benchmark failure remains recorded on the original run; the authorized owner operation uses the same KnowledgeIngestion/source/version/bytes/artifacts, creates a new FR-071 full-run child and audit binding, passes the exact applicable benchmark sections, and can publish only through the normal 17-stage and receipt/manifest gates. Unauthorized users, installation-operator-only assumptions, altered source bytes, active lease, stale scope and duplicate race cannot change the failed row or publish.
- No production rollout, customer grant, live LINE result, test result or deployment is implied by this proposal. Those require separate exact-revision implementation and acceptance evidence.
