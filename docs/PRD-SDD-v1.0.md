Offline-first Project Manager ที่รองรับ business execution และ software execution
ในระบบเดียว — ธุรกิจหนึ่งโปรเจกต์ผสม workstream ได้ 7 โหมด (Software Sprint,
Data Migration, B2B Sales, B2C Campaign, Product Launch, Operations, Business
Expansion) บนโมเดลข้อมูลกลางตัวเดียว — เป็น**โมดูลแรกของ Zuri V2** ที่สร้างเสร็จก่อน
โมดูลอื่นที่จะยกมาจาก V1 (ADR-003: V2 มาแทน V1 ด้วยการ reuse)

| BR-022 | A knowledge object that fails a stage is quarantined with its full failure envelope — `job_id`, `artifact_id`, `stage`, `error_code`, `error_message`, `retry_count`, `first_failed_at`, `last_failed_at`, `pipeline_version` (spec §28) — and classified as retryable, non-retryable or review-required (spec §27). Silent loss is the one outcome forbidden: a corpus that quietly omits what it could not parse reports a completeness it does not have, and every downstream answer inherits that overstatement without a way to detect it. |

SDD-066 made these six tables definition-neutral precisely so a second pipeline definition could share them; `catalogVersion` is one definition's vocabulary, and putting it in a table both definitions write is the union-catalog mistake SDD-066 already refused, relocated from the validator into the schema where no validator can refuse it. `approvedAt` and `approvedBy` are additionally redundant — the `APPROVED` row's own `createdAt` and `decidedByPersonId` are those two facts, and a second copy of a fact is a second answer to it. `vaultId` is resolved per API-010 from scope (FR-057, ADR-022) and is not the ledger's to hold. The cost is named rather than hidden: `evidenceJson` is untyped `text`, so gate evidence is exactly as checkable as the Zod member that writes it and no more — which is why that member is a declared part of this decision instead of left for the first caller to invent, and why a reader must not infer a schema from a sample row. | FR-129; FR-071, FR-110, SDD-042, SDD-057, SDD-066, SDD-070, ADR-030 |
| SDD-076 | A bound repository's **metadata converges on FR-081; its file contents are never persisted.** FR-081(c) makes verbatim persistence the rule for every acquisition channel — raw payloads are replayable evidence, translated by a separate path — and a repository content projection is the first channel where obeying that rule is the defect rather than the discipline. A push delivery's metadata is exactly what `RawExternalRecord` is for and goes there unchanged: head SHA, changed paths, actor, timestamps, under the one envelope with `sourceType: 'WEBHOOK'`. A blob's bytes do not, and the reason is a property of the source rather than a preference about storage: a bound repository is an arbitrary external tree whose contents this repository cannot inspect in advance. CR-006 supplies the concrete case — the repository CR-004 proposes to surface held three spreadsheets of real customer data, tracked in git on a public remote, found by byte-comparing a tree rather than by any check that runs here. Persisting that content would put personal data in a table the erasure path has no route to: FR-022 erases through `Person`/`Customer`, SEC-005 consent is attested on the FR-023 `Customer` row per Business (SDD-053), and rows inside a spreadsheet inside a blob have neither — so the record would be personal data that is unconsented and, by construction, unerasable. The projection therefore reads through and renders; it stores no file content, and both the render and the metadata lane are bounded by a declared path scope, deny-by-default, in the shape SEC-009 already applies to LINE knowledge access. `ProjectRepository.pathScope` is the field that carries such a scope today and is already threaded end-to-end — input schema, service, read model, UI pill, plan and xlsx import — but nothing treats it as a boundary, so it is descriptive metadata that this decision would make load-bearing, which is a change of meaning to state rather than to assume. Named rather than glossed: changed *paths* are metadata, but a path can itself be personal data — CR-006 declines to reproduce the filenames it found for precisely that reason — so the metadata lane is not clean by virtue of being metadata and is bounded by the same scope. **The rejected alternative is the literal reading of FR-081(c)**, and it is rejected explicitly because it is what a reader who finds that clause and not this one will do; a carve-out from a requirement's own default is invisible unless it is written where the default is written. Also rejected, on the ledger's own terms: CR-004's `githubRepoUrl`/`githubBranch`/`githubSyncStatus`/`lastCommitSha`/`lastGithubSyncAt` as columns on `Business`. `Repository` has carried the first two since FR-008 and has been Business-owned since FR-073; the last three are `SyncCursor.cursorValue`, `SyncCursor.lastSuccessAt` and `IngestionRun.status`, which is what a watermark, a success time and a run outcome already mean. Columns on `Business` would additionally cap a Business at one repository, and put a foreign URL and commit SHA on a scope entity — the case BR-002 names with "GitHub id" among its examples. | FR-130; FR-008, FR-073, FR-081, FR-022, BR-002, SEC-005, SEC-009, SEC-015, SDD-037, SDD-043, SDD-053, ADR-038 |
| SDD-077 | A second `knowledge_type` in `business_knowledge` needs its own registered query and its own contract version, because every existing query filters on no type at all. `registeredPredicate` (`src/modules/knowledge/postgres-business-knowledge.js`) builds three predicates — `product_detail`, `product_compare`, and `product_search`'s `ilike` across `product_code`, `name`, `category` and `description` — and the SQL around them constrains `tenant_id`, `business_id`, `sensitivity = 'PUBLIC'` and `is_active`, and nothing else. Today that is safe by accident rather than by design: `knowledge_type` is check-constrained to `'PRODUCT'` in the DDL and `z.literal('PRODUCT')` in `business-contract.js`, and one kind cannot be mistaken for another while there is only one kind. The moment FR-131 widens that constraint, those same three queries answer product questions with rate rows and `product_compare` on two rate codes returns them as products — a wrong answer delivered on the LINE surface with nothing anywhere reporting a problem. So the widening is one decision in four places, not one: the DDL check, the Zod literal, a `contract_version` that is no longer `'1.0.0'`, and a fourth registered query that names the type it serves. Holding rates in a new `ShippingRateMatrix` Prisma model instead, as CR-005 proposes, was rejected on this repository's own terms rather than on taste: it puts one Business's published prices in two stores with two provenance stories — one with `as_of`, `approved_at`, `source_sha256` and an FR-129 signature, one with `updatedAt` — and the second cannot say what a past quotation was priced from. This is deliberately **not** SDD-062 and points the other way. That decision is about `sensitivity`, and says widening what knowledge may CARRY must not widen what is SERVED. Widening `knowledge_type` must widen what is served, because the agent has to be able to quote a rate, so the containment here is a typed query rather than an unchanged filter — and reading SDD-062 as already covering this case is the specific mistake this decision exists to stop. | FR-131; FR-132, FR-047, FR-129, SDD-025, SDD-026, SDD-062, SDD-075 |
