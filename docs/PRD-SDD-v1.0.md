| BR-010 | SQLite is the sole transactional authority for file identity and relations. Filesystem content and `.zuri/cache` are projections/storage, never a second writable relationship database; Business aggregation must query IDs/links and never duplicate a file merely to show it in another view. |

| BR-011 | A LINE event has exactly one reply owner. When stack answering is enabled, `zuri.command-agent` owns signature verification and Reply API transport while `zuri-ai` owns knowledge/provider/answer policy; the legacy local answer path must not also consume the same `replyToken`. |
| BR-012 | Tenant and Business scope are server authority. In production a caller may present only binding identity, destination and binding-scoped credential; inbound `tenantId`/`businessId` never authorize access. A missing, mismatched, inactive, expired or database-unavailable binding fails closed before model or persistence work. |
| BR-013 | Readiness is not activation. Golden evaluation, database probes and canary planning may run while the binding remains `PENDING`; only a separately approved operator action may install hashes or enable one canary. `ACCEPTED_BY_LINE` never proves display or read. |
| BR-014 | An activation correlation owns at most one binding mutation and one LINE canary. Replays return the existing redacted result or fail closed; they never create a second send. |
| BR-015 | LINE transport authentication proves event origin only. Principal, tenant, business, thread audience, capability, sensitivity and vault access come from server-owned identity and policy; thread membership may attenuate access but never elevate it. |
| BR-016 | Profile, WorkspaceMembership, Tenant/Business Membership and Project assignment are distinct authority layers. A lower-level membership never widens a higher-level scope; roles, domains and target identities are server-decided, never accepted as self-asserted client authority. |
| BR-018 | Team membership is never an input to an authorization decision. A Team groups people; it does not grant, widen or imply any scope, role or domain visibility, and the identity resolver never reads it. Stated as a rule rather than left as an intention because a negative invariant holds only while something checks it — `Membership` is the authority record, and merging a grouping into it is what let a single unauthenticated POST mint business-owner authority on 2026-08-17. |
| BR-017 | There is no bare edge. A dependency edge cannot be created without a declared Handoff Contract, and a declared-but-unsatisfied contract does not release its successor. This is a *domain* contract — the obligation between two pieces of work — and is deliberately not the intake envelope of BR-009, which is a *transport* contract governing the shape of a payload crossing the system boundary. The two keep separate names because merging them would put schema validation and project governance in one bucket, leaving the product with one word for two different kinds of "invalid". |
| BR-019 | Integration raw evidence is immutable authority for external acquisition provenance. Market may derive observations from it but never rewrites, re-owns or treats translated payload fields as authority for Tenant/Business/connection/source scope. | FR-081, FR-092, ADR-038 |
| BR-020 | Person is the canonical internal principal; provider/channel subjects are namespaced external attributes. Only active Membership and scope-valid RoleBinding records grant authority, and client, prompt, model or tool values may attenuate but never widen server-owned scope. | FR-094..098, ADR-045 |
| BR-021 | Knowledge ingestion idempotency is keyed on source identity, source version, content hash and pipeline version together (spec §29): reprocessing the same event never creates a second copy of the same knowledge, while a change in any one of the four is a legitimately new derivation rather than a duplicate — which is what makes re-parsing after a parser or embedding-model upgrade safe to run over the whole corpus. This is the ingestion-time rule; FR-081's `sha256(tenantId, connectionId, entityType, externalId, payloadHash)` re-delivery identity remains the raw-boundary rule beneath it, and BR-009's single-envelope discipline still governs how any surface reaches the pipeline at all. |
| BR-022 | A knowledge object that fails a stage is quarantined with its full failure envelope — `job_id`, `artifact_id`, `stage`, `error_code`, `error_message`, `retry_count`, `first_failed_at`, `last_failed_at`, `pipeline_version` (spec §28) — and classified as retryable, non-retryable or review-required (spec §27). Silent loss is the one outcome forbidden: a corpus that quietly omits what it could not parse reports a completeness it does not have, and every downstream answer inherits that overstatement without a way to detect it. |

| SDD-057 | The seventeen-stage knowledge ingestion pipeline reuses the FR-071 execution ledger rather than declaring new models. At the storage layer that is free: `dataPipelineDefinitionId` and `pipelineStageId` are plain `String` columns with no enum, no relation and no check constraint (`prisma/schema.prisma`), so a new definition id and seventeen new `DPS-*` stage ids need no migration. At the contract layer it is not free, and saying so is the point of this decision: `zPipelineEvent` and `zPipelineRunInput` pin `dataPipelineDefinitionId` and `executionContractId` with `z.literal`, `pipelineStageId` is refined against the ten-entry FR-071 catalog (`src/platform/integrations/core/pipeline-tracking-contract.js`), and the tracking service materializes that one catalog on every run creation — so `DPL-KNOWLEDGE-INGEST-V1` is rejected today, and the first implementation slice must parameterize the FR-071 envelope by definition id before it can register anything. | SDD-059 | Chunking is a pure calculator in the knowledge lane, with no persistence and no model. `src/modules/knowledge/chunking.js` takes parsed blocks plus a scope and a provenance and returns chunk objects; it opens no database, writes no table and declares no Prisma model, so the knowledge charter's `owns_models: []` stays true (SDD-057, ADR-050). | SDD-060 | Entity recognition is a seam with a deterministic default, not a model dependency. `extractEntityCandidates` takes an optional `recognizer`; the default recognises legal-form organisation patterns only — `บริษัท … จำกัด`, `ห้างหุ้นส่วนจำกัด …`, `… Co., Ltd.` — because in those the suffix IS the evidence: the grammar announces the type without anyone recognising the name inside it. Person, product, location and the rest of §13's type list need a model, and a model in the knowledge lane would couple Stage 8 to whatever recognises Thai and English text this month (the SDD-059 reasoning, one stage over). An empty seam was rejected as the alternative: shipping a hook with nothing behind it is what makes Stage 15 embedding read as delivered when it is not, and this requirement declines to repeat that shape. `normalized_name` is lexical and uses only the mention itself — trim, collapse, strip the legal wrapper. | SDD-061 | A normalizer that cannot decide reports the ambiguity instead of resolving it — and reports it by withholding the canonical value, not by attaching a warning beside one. A warning next to a readable field is a warning somebody skips: if `canonical` holds a guess, a caller will use it. So an undecidable value returns `canonical: null` with the reason, and the caller has nothing else to read. The case that sets the rule is a Thai date like `25/8/26`, which is 2526 BE or 2026 CE with nothing in the string to separate them — forty-three years apart, both plausible, and no downstream check can catch the wrong one. The same withholding covers an undeclared field order (`5/8/69`, where day and month are both twelve or under) and a date that does not exist (`31/2/2569`, which must never roll into March). Six of §9's twelve categories are normalized; currency, unit, product code, country/region, timezone and identifier format are declined for a stronger reason than missing locale data — their canonical form is business-configured, so one invented here would be wrong in a way that looks authoritative. | FR-114; FR-109, FR-113, SDD-060, BR-021, ADR-050 |
| SDD-063 | The parser produces the block shape Stage 7 already consumes. `parseDocument` returns `structure` as an array of `{ type: heading or text, level, text }`, which is exactly the `blocks` argument `chunkDocument` reads — so Stage 2 hands Stage 7 its input rather than the two agreeing by coincidence across two test suites that each build the shape. **Stage 7 owns the shape**; it existed first and its tests define it, and the parser conforms to it. The seam is held by a test that feeds real parser output straight into `chunkDocument` and asserts on the resulting chunks, because a written statement that two shapes match is prose, and prose is not a contract — the same reason a green governance run does not prove a link resolves. Markdown and plain text are parsed here; PDF, DOCX, OCR and vision layout are not, and are received instead through FR-071's `smartgift.document-intake.v1` front door, which validates someone else's extraction rather than performing one. | FR-115; FR-112, FR-071, FR-109, ADR-050 |
| SDD-062 | Widening what knowledge may carry must not widen what knowledge is served. `business-contract.js` holds two decisions that share a word: the record schema, which says what may be STORED, and the query filter, which says what is SERVED to a public surface. FR-111 widens the first to the four-level lattice and leaves the second at `PUBLIC`, and the two are separate on purpose rather than by oversight. The failure this pins against is not somebody deliberately opening the filter — it is somebody reading `record.sensitivity === 'PUBLIC'`, seeing that the enum now has four values, and correcting the comparison because it looks stale. It is not stale; it is the boundary. The packet stops asserting its own label and verifies it instead: it refuses to wrap a record above `PUBLIC` rather than stamping `PUBLIC` on whatever it was handed, so a future widening of the filter fails loudly instead of leaking. The lattice lives in `src/lib/validation/enums.js` and is named `KNOWLEDGE_SENSITIVITY_LEVELS` because `sensitivity` already means FR-026 action sensitivity (LOW/HIGH) elsewhere; `write-tools.js` rejects an action sensitivity outside LOW/HIGH so a knowledge value cannot reach that path, but `agent/auth-context.js` validates nothing and already defaults to the string `PUBLIC` — so the separation rests on naming there rather than on a guard, and saying so is the point of pinning it. | FR-111; FR-047, SEC-009, SDD-058, ADR-050 |
