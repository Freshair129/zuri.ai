### [ZAI:FR-155 canonical record](requirements/FR-155.md)

> Inventory stock ledger — for a TRACKED product (FR-154), an append-only `StockMovement` (RECEIPT adds, ISSUE removes, ADJUSTMENT carries its own sign, with `reason`, `reference`, `actorId`, `occurredAt`); on-hand is the sum of a product's rows recomputed on every read and never stored on the product, a summary flags on-hand below `safetyStock`, and an UNTRACKED product is refused by code (`INVENTORY_PRODUCT_UNTRACKED`) and reports `null` on-hand, never zero. `ProductLot` (`lot_id`: `code` unique per product, optional factory, manufacture and expiry dates, `receivedQty`, OPEN / QUARANTINE / CLOSED) — a LOT-tracked receipt names a lot by id or creates it by code and the lot's `receivedQty` follows; a receipt into a CLOSED lot is refused. `SerialUnit` (`serial_id`: `serialNo` unique per product, IN_STOCK / RESERVED / ISSUED / RETURNED / SCRAPPED) — a SERIAL-tracked movement names exactly one serial per unit and writes one ledger row per unit; a unit is created IN_STOCK by its receipt, ISSUED by its issue, refused when received while IN_STOCK or issued while not, and ADJUSTMENT is not allowed on a serial product. A plain (NONE) product refuses a lot or a serial on the movement; an ISSUE that would take on-hand below zero is refused. Serial units are created only through the ledger (`GET`-only route); an explicit lot route exists for a dated batch before stock arrives. An ISSUE of a LOT-tracked SKU that names no lot is consumed **FEFO** — first expired, first out — across OPEN lots (unknown expiry last, whatever no lot holds last), one ledger row per lot touched and the allocation in the audit payload; an ISSUE that names a lot may not exceed that lot's on-hand (`INVENTORY_LOT_INSUFFICIENT_STOCK`); a lot listing reports each lot's on-hand from the ledger. Manager authority, FR-072 refusals, one transaction and one audit row per write with `onHandBefore` / `onHandAfter` in the payload.

### [ZAI:FR-156 canonical record](requirements/FR-156.md)

> Inventory recipe / bill of materials at a batch size — `ProductRecipe` (`recipe_id`: `code` unique per Tenant, one row per output SKU and `batchSize` — "the recipe for 10 seats" and "for 20 seats" are two rows on one product, exactly as a gift box has a BOM at 10 / 50 / 100 / 500 sets — with `yieldQty`, `unit`, `notes`, ACTIVE / ARCHIVED, `version`) and `ProductRecipeLine` (a same-Business component SKU with `qty` per batch, optional `unit`, `fixed` for a line that does not scale with the quantity built, such as tooling; a component appears once and is never the output). Pure calculators pick the recipe for a quantity (the largest batch size that fits, else the smallest), explode it (scaled lines multiply by `quantity / batchSize`, fixed lines do not, the output yield follows the batch), compare with on-hand recomputed from the ledger (a fractional requirement is issued as the next whole unit; an uncounted component never blocks) and state the maximum buildable quantity. `GET /api/inventory/recipes/[id]?quantity=` returns that explosion; `POST …/build` is one transaction that issues every counted component through the FR-155 ledger (FEFO for lots) and receives the output SKU when it is counted — refused whole with `INVENTORY_RECIPE_SHORTAGE` and a per-component list when any component is short, and refused when a component or the output is SERIAL-tracked or a LOT-tracked output has no `outputLotCode`. `UPDATE` replaces the fields and, when given, the whole line set; `ARCHIVE` keeps the row; both compare-and-swap on `version`; manager authority, FR-072 refusals, one audit row per write.
