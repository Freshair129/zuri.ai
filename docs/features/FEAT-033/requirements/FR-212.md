| FR-212 | Data pipeline registry and generated projection: `docs/DATA-PIPELINE-MAP.md` carries one JSON registry of the data zuri-ai receives, combines and sends — nodes of kind SOURCE, ENTRY, PROCESS, STORE and RECIPIENT, labelled edges, and chains that run from a source through combine steps to a recipient — and `scripts/data-pipeline-map.mjs`, run by `docs:graph` on every `govern`, turns it into `docs/.data-pipeline-map.json` and the committed `runtime/data-pipeline-map.json`. Every internal node names its owning domain and at least one declared requirement; the generator derives each node's surface level from what exists (an `ENDPOINT` is an existing `src/app/api/**/route.js`, a `UI` an existing `page.jsx`, an `MCP` a tool in the MCP registry, a `WORKER` or `FILE` an existing file), its build status from the FR-124 snapshot (`BLOCKED`, `DECLARED`, `PARTIAL`, `CODE_TESTS`) or `PRODUCTION` only when the node carries written evidence, and its FEATs from the same snapshot. An edge takes the weakest status of the internal nodes it joins (an edge marked unwired is `DECLARED`), and a chain its weakest edge. Generation fails by name on an unknown requirement or decision, a missing surface, a production claim without evidence, an edge to an unknown node, a node no edge touches, a chain whose path does not join or does not run from a SOURCE to a RECIPIENT, and a chain in the document's table that the registry lacks or the reverse; `docs:check` fails when the projection is stale. The projection holds architecture metadata only. | 🟠 implemented locally 2026-09-13 (ADR-085 D2–D4) — `scripts/data-pipeline-map.mjs`, the registry in `docs/DATA-PIPELINE-MAP.md` (20 chains), `doc-graph.mjs` wiring, `runtime/data-pipeline-map.json`, the CI committed-state guard; `tests/unit/data-pipeline-map.test.js` |
