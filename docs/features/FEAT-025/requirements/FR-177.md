| FR-177 | A kitting work order assembles a finished gift set from a recipe with a declared scrap allowance — `KittingWorkOrder` (`KWO-YYYYMMDD-NNN`) explodes one `ProductRecipe` for a planned quantity, and `ProductRecipe.scrapAllowanceFactor` (a fraction in `[0, 0.20]`, default 0, so every recipe written before this requirement explodes exactly as it did) makes the gross issue `ceil(net × (1 + factor))` — the buffer is issued up front rather than fetched mid-line. Completion consumes the components, records assembled and scrapped quantities, blends the component landed costs plus packaging and assembly labour into the finished unit's `costSatang`, and receives the set at `TH_FINISHED_GOODS`. The output must carry a FlowAccount item code matching `^[A-Z0-9]+-[0-9]+\([A-Z0-9_-]+\)$` (model, item count, package code — `TMS06-4(P-16)`), and a run without one is refused. That code is deliberately **not** `Product.code` — FR-154's code pattern has no room for parentheses, and widening it for one integration would be the wrong reading — and equally deliberately not an `ExternalRef` row, which is unique on `(system, value)` installation-wide and carries no `tenantId`, so two Tenants importing from the same factory could not both name their four-item set `TMS06-4(P-16)`. It is one nullable `Product.flowAccountSku` column, unique per `(tenantId, flowAccountSku)`, an attribute and never a key (BR-002), written only by `createProduct` and `setFlowAccountSku`, both of which validate the pattern. Validated where a set is produced rather than where a product is named, because components and packaging are never synchronised to FlowAccount at all. | 🟠 implemented locally 2026-09-10 (ADR-074 D5) — `scrapAllowanceFactor` on `ProductRecipe`, `application/kitting-work-order-service.js`; `tests/integration/fr177-kitting-work-order.test.js` |
