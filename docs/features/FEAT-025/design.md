### [ZAI:FR-175 canonical record](requirements/FR-175.md)

> Inventory valuation is landed cost in integer satang, and domestic single-drop freight is absorbed into it rather than quoted — `StockMovement.costSatang` is the unit landed cost of that row (THB × 100, never a float, the ADR-065 D2 money rule). `landedUnitCostSatang = factoryCostSatang + ceil(seaFreight/batch) + ceil(duty/batch) + ceil(inboundTruck/batch) + customizationPerUnit + kittingPerUnit`, each shared cost divided by the batch and rounded up to the satang so a batch is never valued below what it cost. The inbound truck defaults to the flat 250,000 satang (2,500 THB) single-drop rate, which is why a standard quote shows delivery as 0.00 and must carry no separate freight line — a second drop or an island crossing is a different service and belongs to Commerce. Valuation across receipts is moving weighted average, recomputed from the ledger like every other inventory number.

### [ZAI:FR-177 canonical record](requirements/FR-177.md)

> A kitting work order assembles a finished gift set from a recipe with a declared scrap allowance — `KittingWorkOrder` (`KWO-YYYYMMDD-NNN`) explodes one `ProductRecipe` for a planned quantity, and `ProductRecipe.scrapAllowanceFactor` (a fraction in `[0, 0.20]`, default 0, so every recipe written before this requirement explodes exactly as it did) makes the gross issue `ceil(net × (1 + factor))` — the buffer is issued up front rather than fetched mid-line. Completion consumes the components, records assembled and scrapped quantities, blends the component landed costs plus packaging and assembly labour into the finished unit's `costSatang`, and receives the set at `TH_FINISHED_GOODS`. The output must carry a FlowAccount item code matching `^[A-Z0-9]+-[0-9]+\([A-Z0-9_-]+\)$` (model, item count, package code — `TMS06-4(P-16)`), and a run without one is refused. That code is deliberately **not** `Product.code` — FR-154's code pattern has no room for parentheses, and widening it for one integration would be the wrong reading — and equally deliberately not an `ExternalRef` row, which is unique on `(system, value)` installation-wide and carries no `tenantId`, so two Tenants importing from the same factory could not both name their four-item set `TMS06-4(P-16)`. It is one nullable `Product.flowAccountSku` column, unique per `(tenantId, flowAccountSku)`, an attribute and never a key (BR-002), written only by `createProduct` and `setFlowAccountSku`, both of which validate the pattern. Validated where a set is produced rather than where a product is named, because components and packaging are never synchronised to FlowAccount at all.

### [ZAI:FR-179 canonical record](requirements/FR-179.md)

> A stored unit that ages and can be restored by an operation is guarded on issue, not merely reported — `Product.maintenanceIntervalDays` and `Product.maxStorageDays` (both nullable, so a product with neither behaves exactly as before) and `ProductLot.lastMaintainedAt` make a lot's storage age `now − (lastMaintainedAt ?? manufacturedAt)`. At the maintenance interval the lot is **due**: surfaced as a task, never blocked. Past `maxStorageDays` it is **refused** for issue and for kitting until a maintenance is recorded, which resets the clock. The generalisation past "battery" is deliberate — the rule is about a unit that degrades in storage and is restored by an operation, which is as true of a lithium cell needing a 180-day recharge as of a calibrated instrument. FEFO (FR-155) still chooses which lot goes first; this says which lots may go at all.

### [ZAI:FR-180 canonical record](requirements/FR-180.md)

> Available-to-Promise subtracts what is already spoken for, in two tiers — `StockReservation` holds one product's quantity for one purpose: `QUOTE` (soft, expiring, 7 days by default) or `ORDER` (committed against a confirmed sales order), so `ATP = onHand − Σ committed − Σ live quote reservations`. A reservation is never deleted: it moves to `RELEASED`, `CONVERTED` or `EXPIRED`, so "why could we not promise those 500 on Tuesday" stays answerable. Expiry is evaluated on read against the clock rather than by a sweeper, so an ATP figure is correct even when no worker has run. Reservations never write the stock ledger — a reservation is a promise and the ledger is physical fact — and the maximum buildable set count is computed from ATP rather than on-hand, so two quotes cannot both promise the same tumblers.

### [ZAI:FR-184 canonical record](requirements/FR-184.md)

> Inventory physical stocktake reconciles an authorized Business's existing located ledger through the existing Inventory surface — `POST /api/inventory/stocktakes/preview` accepts only normalized tracked `NONE` or `LOT` lines with explicit location and lot identity, integer non-negative counts, and no duplicate keys; it persists a read-only `InventoryStocktake` preview containing the expected snapshot version/hash, expected/count/variance and normalized input without writing movements. `POST /api/inventory/stocktakes/commit` revalidates the stored preview and current Business scope, acquires the shared lock-only `InventoryLedgerFence` before its ledger read, refuses a changed snapshot with `409 INVENTORY_STOCKTAKE_SNAPSHOT_STALE`, and atomically appends every signed `ADJUSTMENT` through FR-155 `appendMovement` plus one audit event or writes nothing. The Business-scoped idempotency key returns the same saved result for an identical retry and refuses a different payload; zero variance is a durable no-op; SERIAL lines and untracked/service products are explicitly refused until a serial-observation contract exists. Backup export/import preserves the fence and stocktake rows through the declared `inventoryStocktakeRecovery` manifest in FK order, while a legacy snapshot reports the recovery state unavailable rather than claiming preservation.
