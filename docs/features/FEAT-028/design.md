# FEAT-028 — Org Employment & Legal Entity — separating "who works here" from "who may log in here": a new `Employment` HR assignment record (title, type, lifecycle status) that `resolveViewer` never reads, with system access shown as a column derived FROM `Membership` rather than the reverse; and moving `LegalEntity` from `Portfolio` to `Tenant` so a Business can only reference a legal entity within its own isolation boundary, splitting its VAT branch registrations into `TaxRegistrationBranch` so an operating site (a warehouse, say) is never asked to carry a tax identity it does not have (ADR-078, 2026-09-12)

## Included requirements

### [ZAI:FR-193 canonical record](requirements/FR-193.md)

> `Employment` is a new HR assignment record — `personId`, `tenantId`, `businessId`, optional `branchId`, `employeeNo` (was `Membership.employeeRef`), `title`, `employmentType` (EMPLOYEE / CONTRACTOR / INTERN / OWNER_OPERATOR) and a lifecycle status (ACTIVE / ON_LEAVE / ENDED) — separate from `Membership`'s access grant (ADR-078 D1). Before this, `people-service.js` built the HR roster by reading `Membership` directly, so a shareholder's tenant-wide OWNER grant read as an employee, a suspended staff member vanished from the roster instead of showing suspended, a consultant with access but no employment could not be distinguished from staff, and the LINE-originated Persons who hold no Membership at all could never appear. `resolveViewer` and the rest of `src/modules/identity/` never read `Employment` (ADR-037 D1's discipline, applied here); `people-service.js` now derives one column, `hasSystemAccess`, FROM `Membership`, never the reverse. `Membership.employeeRef` and `Membership.branchId` are dropped in the same migration that backfills them into `Employment`, after the backfill runs; a tenant-wide grant with an `employeeRef` (production's one such row) is not backfilled, because standard HR has no group-level employment — the migration names the skipped row instead of guessing a Business for it. HR Remove is available only to scoped OWNER or live OPERATOR, separately from access withdrawal; ending retains history and never revokes Membership.

### [ZAI:FR-194 canonical record](requirements/FR-194.md)

> `LegalEntity` moves from `portfolioId` to `tenantId` (ADR-078 D2) — before this it carried no Tenant column at all, which put it above the BR-001 isolation boundary: two Businesses in different Tenants could share one legal entity, and a tenant-scoped RLS policy had no column to filter on. `Business.legalEntityId` now has a composite FK to `LegalEntity(id, tenantId)`, so a Business may only reference a LegalEntity in its own Tenant; `createBusiness` carries the same check in application code for the SQLite dev/test path a compound FK cannot express there. `TaxRegistrationBranch` (`legalEntityId`, `branchCode`, `name`, `address`) is split out of `Branch.taxBranchCode`: a VAT branch code (ประมวลรัษฎากร ม.86, ภ.พ.20) is a fact about the legal entity's own tax registration, not about an operating site — a warehouse Branch has none, and `Branch` gains `kind` (SITE / WAREHOUSE / KITCHEN / OFFICE) to say what it IS independently of that. `billing-invoice-service.js` reads `branch.taxRegistrationBranch.branchCode`, refuses `422 BILLING_TAX_BRANCH_NOT_CONFIGURED` when a TAX_INVOICE/ABB_TAX_INVOICE has none and `422 BILLING_TAX_BRANCH_MISMATCH` when the linked one belongs to a different LegalEntity than the Business; the old application-code portfolio comparison is retired, while the `409 BILLING_SHARED_LEGAL_ENTITY` refusal for two Businesses sharing one LegalEntity stays correct and unchanged.
