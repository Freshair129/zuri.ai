| FR-194 | `LegalEntity` moves from `portfolioId` to `tenantId` (ADR-078 D2) — before this it carried no Tenant column at all, which put it above the BR-001 isolation boundary: two Businesses in different Tenants could share one legal entity, and a tenant-scoped RLS policy had no column to filter on. `Business.legalEntityId` now has a composite FK to `LegalEntity(id, tenantId)`, so a Business may only reference a LegalEntity in its own Tenant; `createBusiness` carries the same check in application code for the SQLite dev/test path a compound FK cannot express there. `TaxRegistrationBranch` (`legalEntityId`, `branchCode`, `name`, `address`) is split out of `Branch.taxBranchCode`: a VAT branch code (ประมวลรัษฎากร ม.86, ภ.พ.20) is a fact about the legal entity's own tax registration, not about an operating site — a warehouse Branch has none, and `Branch` gains `kind` (SITE / WAREHOUSE / KITCHEN / OFFICE) to say what it IS independently of that. `billing-invoice-service.js` reads `branch.taxRegistrationBranch.branchCode`, refuses `422 BILLING_TAX_BRANCH_NOT_CONFIGURED` when a TAX_INVOICE/ABB_TAX_INVOICE has none and `422 BILLING_TAX_BRANCH_MISMATCH` when the linked one belongs to a different LegalEntity than the Business; the old application-code portfolio comparison is retired, while the `409 BILLING_SHARED_LEGAL_ENTITY` refusal for two Businesses sharing one LegalEntity stays correct and unchanged. | ✅ implemented 2026-09-12 — ADR-078 D2/D3; migration `20260912130000_org_employment_legal_entity.sql` APPLIED on production 2026-09-12. The "zero rows" precondition was re-confirmed directly before the apply (LegalEntity 0, Branch 0) and re-asserted by the migration itself; the earlier note that it could not be checked from that session is superseded. This migration is the wave's only destructive one — it drops `LegalEntity.portfolioId`, `Branch.taxBranchCode`, `Membership.branchId` and `Membership.employeeRef`, all verified gone afterwards |
