| FR-193 | `Employment` is a new HR assignment record — `personId`, `tenantId`, `businessId`, optional `branchId`, `employeeNo` (was `Membership.employeeRef`), `title`, `employmentType` (EMPLOYEE / CONTRACTOR / INTERN / OWNER_OPERATOR) and a lifecycle status (ACTIVE / ON_LEAVE / ENDED) — separate from `Membership`'s access grant (ADR-078 D1). Before this, `people-service.js` built the HR roster by reading `Membership` directly, so a shareholder's tenant-wide OWNER grant read as an employee, a suspended staff member vanished from the roster instead of showing suspended, a consultant with access but no employment could not be distinguished from staff, and the LINE-originated Persons who hold no Membership at all could never appear. `resolveViewer` and the rest of `src/modules/identity/` never read `Employment` (ADR-037 D1's discipline, applied here); `people-service.js` now derives one column, `hasSystemAccess`, FROM `Membership`, never the reverse. `Membership.employeeRef` and `Membership.branchId` are dropped in the same migration that backfills them into `Employment`, after the backfill runs; a tenant-wide grant with an `employeeRef` (production's one such row) is not backfilled, because standard HR has no group-level employment — the migration names the skipped row instead of guessing a Business for it. HR Remove is available only to scoped OWNER or live OPERATOR, separately from access withdrawal; ending retains history and never revokes Membership. | ✅ implemented 2026-09-12 — ADR-078 D1; `employment-service.js` (create / on-leave / reinstate / end); `people-service.js` reads Employment; `rbac-service.js`'s `assertEmployee` renamed to `assertTenantMember` (it checked Membership, not employment). Migration `20260912130000_org_employment_legal_entity.sql` APPLIED on production 2026-09-12 |
