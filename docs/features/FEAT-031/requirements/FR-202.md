| FR-202 | A SKU is one combination of its master's variant axes, and the same combination cannot exist twice (BR-039): `ProductMaster.variantAxes` is the ordered list of axes that distinguish its SKUs (`["color","size"]`, fixed at creation), each SKU carries `variant` (one value per declared axis; a missing axis is `INVENTORY_VARIANT_AXES_INCOMPLETE`, an undeclared one `INVENTORY_VARIANT_AXIS_UNKNOWN`), and the service derives `variantKey` — the normalized `axis=value\|axis=value` fingerprint — unique per master by index, archived or not, so a second SKU for the same combination is refused with `INVENTORY_PRODUCT_VARIANT_EXISTS` naming the first (and REACTIVATE is the answer when the first is archived). The legacy `color` / `material` columns feed a same-named axis when `variant` is silent. A master that declares no axes has no key and enforces nothing (reported as `MASTER_WITHOUT_AXES`); for every master the exact-match lookalike guard refuses a new SKU whose normalized name, colour, material and variant match a live SKU under the same master (`INVENTORY_PRODUCT_LOOKALIKE`) unless the caller passes `allowLookalike`, which the audit row records. `UPDATE` may correct a variant; it is re-keyed and re-checked. | 🟠 implemented locally 2026-09-13 (ADR-083 D2) — `variantValues` / `variantKeyFor` / `lookalikeFingerprint` / `normalizeToken` in `inventory-governance.js`, the NULL-tolerant unique index `(productMasterId, variantKey)`, `createProduct` and the UPDATE path; migration `20260913120000_inventory_sku_governance` APPLIED on production 2026-09-13 (owner-instructed, ADR-057; ledger row written, effect verified: 3 + 6 columns, both tables with forced RLS, 0 masters to backfill) and main 52c9881e deployed; AC-202.1, AC-202.2 |
