## MSP scheduling follow-up — 2026-10-24

The preserved delivery cell above describes the original CRM-only implementation.
The owner requested closing MSP's invocation gap under the same retention rule.
The [bounded maintenance plan](../../../plans/MSP-RETENTION-SCHEDULER-20261024.md)
defines the operator-authenticated API-011 caller, Tenant windows, live-job fence,
nightly host action and separate qualification/deployment gates. The requirement
statement, ID and feature membership remain unchanged. A configured horizon
alone does not prove that a sweep runs; runtime results must name the actual
artifact, schedule and audit evidence. Legacy vault/passport TTL, raw LINE and
trace retention remain outside this bounded invocation fix.

## Integration and Agent retention follow-up — 2026-11-12

Two additional owning-domain sweepers now implement the declared 90-day windows:
Integration replaces expired `LINE_OA` `RawExternalRecord.payloadJson` values with
`RETENTION_EXPIRED` tombstones, and Agent redacts expired `AgentTraceEvent` turns
through the existing trace redaction path. Both keep their envelope metadata,
honour Tenant-shortened windows, and have bodyless deployment-authenticated
routes called by the shared retention worker after CRM. The Agent sweep protects
open MSP erasures and pending memory delivery; Integration protects active LINE
jobs and `ADMITTING` outbox rows. These are source implementations only: no
deployment schedule is configured or evidenced yet. The canonical requirement
row, its identity and its source-preserved metadata above are unchanged.

**2026-11-13 hardening and dry-run follow-up.** Every retention read now treats
an override as valid only when `windowDays` is a safe integer of at least one;
valid values remain clamped to the installation default. An invalid persisted
value is ignored in favor of that default, logged as a structured
`RETENTION_OVERRIDE_INVALID` line without record content, marked on the
Tenant's counts and listed in the run audit. Snapshot restore refuses override
rows unless `tenantId` is non-empty, `dataClass` is declared, and the window is
from one day through that class's installation default. No database CHECK
constraint is shipped here; that constraint remains a follow-up.

All four retention routes accept one strict `dry_run=true|false` parameter.
`true` uses the ordinary eligibility and skip rules without retention writes or
audit events, and returns aggregate counts plus per-Tenant counts and
status/failure fields. CRM retention may report `archiveFailed`,
`archiveFailureReason`, `settleFailed`, `settleFailureReason` and `invalidOverrideIgnored`; archive
expiry may report `skippedReason` and `failureCode`. The dry-run response never
includes message or Customer content, Customer or manifest ids, or archive paths. Archive
expiry simulates the in-run key-destruction order in memory and uses read-only
`lstat` file inspection plus a permission probe; its production storage
readiness precheck still runs. The shared worker's
`--dry-run` previews CRM message retention, archive expiry, Integration and
Agent. Before the first scheduled run, an operator must run that command inside
the `web` container and compare per-Tenant counts. A real CRM response may
include `manifests` inside `countsByClass`, with `tenantId`, `manifestId`, `runId`
and `manifestHash` per entry. The CRM sweep targets every eligible CRM message
past the Tenant's effective window (24 months by default, shorter with an
override) that is not skipped by the non-terminal-job, tombstone,
archive-failure or deferral rules. No deployment schedule or production run is
claimed.
