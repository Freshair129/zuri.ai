# STD-Multi Agent Workflow S-01

สถานะ: candidate — ใช้เป็นมาตรฐานการทำงานแบบ bounded จนกว่าเจ้าของจะ promote เป็น stable

## 1. เป้าหมายและขอบเขต

S-01 กำหนดลำดับการทำงานตั้งแต่รับโจทย์จนถึงปิดงานของ zuri-ai โดยใช้
`ROADMAP.md` เป็น source of truth, ใช้ DAG เพื่อเลือก wave ที่ขนานได้ และใช้
Luna Max เป็น worker กับ Astra เป็น reviewer แยกจากผู้ประสานงานหลัก

S-01 ไม่อนุญาตให้เปลี่ยน `review`, `isolated`, `hosted-ci`, `production`,
`owner`, `MSP`, `GKS` หรือ `PORL` ให้เป็น `done` เพียงเพราะโค้ดหรือ PR ผ่าน
การตรวจระดับที่แคบกว่า

## 2. บทบาท

| บทบาท | หน้าที่ | สิ่งที่ห้ามทำ |
|---|---|---|
| Orchestrator | อ่าน SOT, สร้าง DAG/waves, ตรวจ conflict, รวมผล, รัน gate สุดท้าย | เขียนงานซ้ำโดยไม่ตรวจ ancestry/evidence |
| Luna Max worker | ทำงานใน isolated branch ตาม task เดียวและส่งหลักฐาน | แก้ shared source, deploy, ใช้ credential, ปิด owner gate |
| Astra reviewer | ตรวจ contract, diff, evidence boundary และ GO/NO-GO | อนุมัติ production จาก fixture/local proof |
| Owner/Operator | อนุมัติ scope, credential, migration, production/PORL action | ให้ agent พิมพ์ secret หรือข้าม rollback |

## 3. ลำดับมาตรฐาน

1. รับโจทย์และแปลงเป็น acceptance, success และ exit criteria
2. ตรวจ parent/peer documents และระบุ complexity เป็น C-1, C-2 หรือ C-3
3. ตรวจ SOT และค้นหา capability/duplicate key ก่อนสร้าง task ใหม่
4. สร้างหรืออ่าน DAG จาก `depends_on`; แบ่ง topological waves
5. คัดเฉพาะ task ที่ dependency เสร็จและผ่าน lane/owner/shared-file conflict check
6. ส่ง task ให้ worker คนละ branch พร้อม contract, file scope, timeout และ output schema
7. ให้ worker ส่งผลเป็น `GO`, `NO-GO`, `NO-CHANGE` หรือ `BLOCKED` พร้อมหลักฐาน
8. ให้ Astra review เฉพาะ diff/evidence ที่ worker ส่งกลับ; ห้ามถือ intent เป็น proof
9. Orchestrator รวมเฉพาะผลที่ไม่ชนกัน แล้วรัน governance, focused tests, build และ diff check
10. เปิด PR และรอ hosted checks แบบมีขอบเขตเวลา; E2E ที่ skipped ต้องบันทึกว่า skipped
11. Merge เฉพาะเมื่อ head SHA ตรง, required checks terminal และ diff ผ่าน reviewer
12. แยก post-merge production/owner/MSP/GKS/PORL gates เป็นงานถัดไป พร้อม rollback และ receipt
13. อัปเดต canonical SOT แล้ว regenerate projections; ห้ามแก้ generated output ด้วยมือ

## 4. กติกา wave และการขนาน

- งานอยู่ wave เดียวกันได้เมื่อไม่มี dependency path ระหว่างกันเท่านั้น
- Same-wave ไม่ได้แปลว่า merge ได้ทันที ต้องตรวจ shared files, schema, migration,
  document registry, ID ledger, external repository และ owner lane เพิ่มเติม
- งานที่มี production, credential, external provider, MSP/GKS หรือ PORL เป็น dependency
  ให้ถือเป็น gate งานหนึ่ง ไม่เอาไปปนกับ code-only wave
- ถ้า worker สองตัวต้องแก้ canonical SOT, PRD, FEATURES, roadmap หรือ ID ledger
  ให้มี integrator เพียงคนเดียวเป็นผู้ compose และ regenerate graph

## 5. Worker contract และ stop rule

ทุก dispatch ต้องระบุ:

- task id เดียว, branch/worktree เดียว และ file scope ที่ไม่ทับ lane อื่น
- current base SHA และ dependency ที่ตรวจแล้ว
- acceptance/exit criteria และคำสั่งตรวจแบบ bounded
- ห้าม deploy, migration production, credential หรือ external write โดยไม่มี owner gate
- ผลลัพธ์บังคับ: status, root cause/decision, files changed, commit/PR, checks,
  skipped checks, blocker และ next action

Stop rule:

- ถ้าไม่มีผลลัพธ์ใน 10 นาที ให้ตรวจ handle และส่งคำสั่งสั้นเพื่อขอ checkpoint
- ถ้ายังไม่มีความคืบหน้าหลัง checkpoint ให้หยุด worker และบันทึก `BLOCKED` หรือ `NO-GO`
- ห้าม restart ซ้ำเพียงเพราะ observation timeout; ตรวจ authoritative process/CI state ก่อน
- ห้ามรอ full CI แบบไม่มีกำหนด; ใช้ focused checks ระหว่างทางและระบุ hosted run ที่ยัง live
- งานที่พบว่า code/PR มีอยู่แล้วต้องรายงาน `NO-CHANGE` และ evidence ไม่สร้าง implementation ซ้ำ

## 6. Evidence boundary

| หลักฐาน | พิสูจน์ได้ | ยังพิสูจน์ไม่ได้ |
|---|---|---|
| fixture/unit/local | behavior ของ slice ใน environment นั้น | hosted, production, provider จริง |
| isolated acceptance | branch/worktree acceptance ตาม receipt | main merge หรือ production readiness |
| hosted CI | commit ที่ CI รันผ่าน | deployment, real provider, owner approval |
| production receipt | action จริงบน target พร้อม timestamp/rollback | MSP/GKS/PORL ที่ไม่ได้อยู่ใน receipt |
| owner approval | สิทธิ์เริ่ม gated action | ผลลัพธ์ของ action ที่ยังไม่รัน |

ทุก status ใน SOT ต้องสอดคล้องกับ proof scope ที่ต่ำที่สุดของ acceptance ที่ยังค้าง
และต้องบันทึก `NOT_RUN`, `SKIPPED`, `UNKNOWN` หรือ `CONTRADICTED` ตามจริง

## 7. Definition of Done

งานจะเป็น `done` ได้เมื่อ acceptance, success และ exit criteria ครบ, หลักฐานตรง scope,
focused/full checks ที่ประกาศไว้รันจริง, governance/build ผ่าน, PR merge แล้วเมื่อจำเป็น,
documentation และ generated views สด และไม่มี owner/production/MSP/GKS/PORL gate ที่ยังค้าง

ถ้า code เสร็จแต่ gate ภายนอกยังค้าง ให้ใช้ `review` หรือ `in-progress` พร้อมระบุ gate
ห้ามใช้เปอร์เซ็นต์จากจำนวน task อย่างเดียวเพื่ออ้าง production readiness
