## 1. คำถามที่ต้องตัดสินจริง ๆ

ไม่ใช่ "A หรือ B" ลอย ๆ แต่คือ:

> **"ธุรกิจ" (Business) จะเป็น context กลางที่ทุกโมดูลรู้จัก หรือจะเป็นเรื่องของ
> Project Manager โมดูลเดียว?**

ตอบข้อนี้ได้ คำตอบ A/B ตามมาเอง — ที่เหลือในเอกสารนี้คือราคาของแต่ละคำตอบ

## 2. ข้อเท็จจริงที่นับได้

### Zuri v1 (`G:\zuri`) — ระบบที่ใช้งานจริงอยู่

| สิ่งที่วัด | ค่า |
|---|---|
| Prisma models | **94** (PostgreSQL) |
| การอ้าง `tenantId` ในสคีมา | **255 จุด** |
| การอ้าง `businessId` | **0** |
| API route handlers | 209 |
| หน้า dashboard | 68 |
| repository layer | 66 ไฟล์ |
| ไฟล์เทสต์ | ~300 |

| Stack | Next 14.2.35 · React 18.3.1 · Prisma 5.22 · Zod 3.23.8 |

### zuri-v2-lab (repo นี้)

| สิ่งที่วัด | ค่า |
|---|---|
| Prisma models | 20 (SQLite, string enums — ย้าย Postgres ได้โดยไม่เปลี่ยน semantics) |

**Stack ตรงกันเป๊ะ** แปลว่าไม่มีต้นทุนด้าน framework/tooling ในทั้งสองทาง

### กับดักที่ต้องรู้ก่อนตัดสิน: คำว่า "tenant" คนละความหมาย

| | ความหมายใน Zuri v1 | ความหมายใน PM (v2-lab) |
|---|---|---|
| `Tenant` | **หนึ่งร้าน/หนึ่งธุรกิจ** — มี `tenantSlug`, `lineOaId`, `plan`, branding, `ownerEmployeeId` | **ร่มการแยกข้อมูล** ที่ครอบได้หลาย Business |
| ธุรกิจในเครือ | ไม่มีแนวคิดนี้ (ไม่มี parent/group/portfolio ในสคีมาเลย) | Portfolio → Tenant → Business |
| พนักงาน | `Employee` ผูก `tenantId` + มี `passwordHash` ของตัวเอง | `Person` + `Membership` ข้ามธุรกิจได้ |

ผลที่ตามมาในระบบวันนี้ ที่ตรวจสอบได้: **เจ้าของที่มี 2 ร้าน = 2 tenants =
2 บัญชีล็อกอิน, ลูกค้าคนละชุด, LINE OA คนละตัว, แชร์ข้อมูลกันไม่ได้เลย**
สคีมาปัจจุบันไม่มีที่ให้เขียนคำว่า "เครือ" ลงไป

## 3. Option A — merge เป็นโมดูลใน Zuri v1

**ทำอะไรบ้าง**
1. ย้าย `src/modules/project-manager` เข้า v1, ลงทะเบียน nav ใน `modules.js`
2. เขียน adapter: `v1.Tenant → PM.Business` (auto สร้าง Portfolio/Tenant ครอบ 1:1 ต่อร้าน)
3. ย้าย 20 models ไป Postgres (namespace/schema แยก) — mechanical ตาม DB-MIGRATION-NOTES
4. เอา endpoint import/backup ไปอยู่หลัง auth ของ v1

**ได้อะไร:** โมดูลบริหารโครงการ 7 โหมด + progress engine + 4 ช่องทาง intake
เข้าไปอยู่ในของที่ลูกค้าใช้อยู่แล้ว โดยไม่แตะโมดูลเดิมสักตัว

**เสียอะไร / เพดานอยู่ตรงไหน**
- Portfolio/Business มองไม่เห็นจากฝั่ง CRM/POS/Inbox — คำถาม "ธุรกิจในเครือแชร์ CRM"
  ยังตอบไม่ได้เหมือนเดิม
- FR-020 (adaptive shell) จะทำงานในโหมดธุรกิจเดียวตลอด — switcher ไม่มีวันโผล่
  เพราะ 1 tenant = 1 business เสมอ
- adapter ชั้นนั้น (~ScopeContext wrapper + การ map สิทธิ์) เป็น**งานที่ทิ้งทีหลัง**
  ถ้าวันหนึ่งไป B
- ทับซ้อนกับของเดิม: v1 มี `model Task` (ผูก customer, FOLLOW_UP, ใช้ใน CRM) อยู่แล้ว
  ต้องตอบให้ชัดว่า "งาน" ของ PM กับ "งาน" ของ CRM คนละของ ไม่งั้นผู้ใช้สับสน

**ความเสี่ยง:** ต่ำ (ไม่แตะ 94 models เดิม, ไม่แตะ auth, ไม่แตะ production data)
**ขนาดงาน:** ปานกลาง — งานหลักคือ adapter + ย้าย DB provider

## 4. Option B — ยกเป็นฐานของ Zuri v2

**ต้นทุนจริงไม่ใช่ "port โมดูลเข้ามาทีละตัว" แต่คือการเปลี่ยน scope ของทั้งระบบ**

สิ่งที่ต้องเกิดขึ้นจริง:
1. เพิ่มมิติ `business_id` ให้ข้อมูลที่วันนี้ผูกกับ `tenant_id` — **255 จุดอ้างอิงใน 94 models**
   (ไม่ใช่ทุกจุดที่ต้องแก้ แต่ทุกจุดต้องถูก*ตัดสิน*ว่าอยู่ระดับเครือหรือระดับธุรกิจ)
2. เปลี่ยน identity: `Employee(tenantId, passwordHash)` → `Person` + `Membership`
   หลายธุรกิจ = ต้องแตะ auth ของระบบที่มีผู้ใช้จริง
3. ย้าย 209 route handlers + 66 repositories ให้อ่าน scope ใหม่
4. ไมเกรตข้อมูลจริง (ไม่ใช่ copy ไฟล์): export → migrate schema → import + reconcile
5. ทำใหม่ให้ผ่านเทสต์เดิม ~300 ไฟล์

**ได้อะไร:** ทุกโมดูลรู้จัก "ธุรกิจ" — เครือเดียวแชร์ CRM ได้, roll-up ข้ามธุรกิจได้,
เจ้าของล็อกอินครั้งเดียวเห็นทุกร้าน, PM ที่สร้างเสร็จแล้วกลายเป็น shell ของ v2 ทันที
(scope model + isolation guard + module registry + Heritage shell + audit + backup
มีอยู่แล้วและมีเทสต์คุม)

**ความเสี่ยง:** สูง — แตะ auth + scope ของระบบที่มีลูกค้าใช้อยู่ พร้อม LINE OA ที่ผูก
กับ tenant รายตัว **ขนาดงาน:** ใหญ่ ระดับ versioned architecture migration ไม่ใช่ refactor

## 5. เทียบตรง ๆ

| | A — โมดูลใน v1 | B — ฐานของ v2 |
|---|---|---|
| แตะระบบที่ใช้งานอยู่ | ไม่ (เพิ่มโมดูล) | ใช่ (scope + auth ทั้งระบบ) |
| ตอบโจทย์ "เครือแชร์ CRM" | **ไม่ได้** | ได้ |
| ใช้ FR-020 switcher ได้จริง | ไม่ (1 tenant = 1 business) | ได้ |
| งานที่ต้องทิ้งทีหลัง | adapter ชั้น scope | ไม่มี |
| ความเสี่ยงต่อลูกค้าปัจจุบัน | ต่ำ | สูง ต้องมีแผนไมเกรต + rollback |
| เวลาถึงมือผู้ใช้ | เร็ว | ช้า |
| งานที่ทำไปแล้วใน repo นี้ถูกใช้ | ~70% (ตัว PM) | ~100% (PM + shell + scope) |

## 6. เส้นทางที่สาม: A ก่อน แล้ว B (และเงื่อนไขที่ทำให้ไม่เป็นงานทิ้ง)

เป็นทางที่สมจริงที่สุด **ถ้า** ตกลง 3 ข้อนี้ตั้งแต่วันนี้:

1. **ประกาศคำศัพท์กลางเดี๋ยวนี้** — Portfolio / Tenant(=ร่มแยกข้อมูล) / Business / Workspace
   ตามที่ repo นี้นิยาม และเลิกใช้คำว่า tenant ในความหมาย "ร้าน" ในเอกสาร/โค้ดใหม่
2. **ตารางใหม่ทุกตัวใน v1 ตั้งแต่วันนี้ต้องมีมิติธุรกิจ** (อย่างน้อยคอลัมน์ที่เติมได้ทีหลัง)
   ไม่งั้นหนี้ 255 จุดจะโตขึ้นทุกสัปดาห์
3. **adapter ต้องบางและอยู่ที่เดียว** — map `v1.Tenant → PM.Business` ในไฟล์เดียว
   เพื่อให้วันที่ไป B แค่ลบไฟล์นั้นทิ้ง

ถ้า 3 ข้อนี้ไม่ถูกบังคับ "A ก่อนแล้วค่อย B" จะกลายเป็น "A ตลอดไป" เพราะต้นทุน B
จะแพงขึ้นเรื่อย ๆ ตามจำนวนตารางที่เพิ่มแบบผูก tenant

## 7. สามคำถามที่ชี้ขาด

| # | คำถาม | ถ้า "ใช่" | ถ้า "ไม่" |
|---|---|---|---|
| 1 | มีลูกค้า (หรือตัวเราเอง) ที่มีหลายธุรกิจในเครือ **ตอนนี้** และเจ็บกับการแยกข้อมูลจริงหรือยัง | → B (หรือ A+เงื่อนไขข้อ 6 ทันที) | → A |
| 2 | ยอมหยุด/ชะลอฟีเจอร์ใหม่ของ v1 ระหว่างไมเกรต scope ได้ไหม | → B ทำได้จริง | → A ก่อน |
| 3 | "ธุรกิจ" ต้องปรากฏใน CRM/POS/Inbox ด้วย หรือแค่ในหน้าบริหารโครงการก็พอ | ทุกโมดูล → B | แค่ PM → A |

## 8. คำแนะนำ

**ปลายทางคือ B — แต่ยานพาหนะวันนี้คือ A พร้อมเงื่อนไขข้อ 6**

เหตุผล: โมเดล Portfolio/Tenant/Business/Workspace พิสูจน์แล้วในของจริง (129+28 เทสต์,
4 ช่องทาง intake, adaptive shell) และ v1 วันนี้ **เขียนคำว่า "เครือ" ลงในสคีมาไม่ได้เลย**
— ข้อจำกัดนี้จะไม่หายไปเอง แต่การรื้อ scope ของระบบที่มีลูกค้าใช้อยู่ตอนที่ยังไม่มี
ลูกค้าเครือรายแรก คือการรับความเสี่ยงสูงสุดในจังหวะที่ผลตอบแทนยังเป็นศูนย์

**Trigger ที่ทำให้เปลี่ยนเป็น B ทันที:** ลูกค้าเครือรายแรกที่ต้องการ CRM/รายงานข้ามธุรกิจ
หรือวันที่เราเองเปิดธุรกิจที่สองภายใต้บัญชีเดียวกัน

**ถ้าเลือก A ล้วน (ไม่เอาเงื่อนไขข้อ 6)** ก็เป็นคำตอบที่ถูกต้องได้ — แต่ต้องยอมรับว่า
FR-020 และงานสถาปัตยกรรมขอบเขตใน repo นี้จะเป็นการลงทุนที่ยังไม่ได้ใช้จนกว่าจะถึงวันนั้น
